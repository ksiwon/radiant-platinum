## 1. 결정

### 1.1 재검증보다 하네스 예산을 먼저 고친다 (물음 1·2)

**순서: 하네스 수정 → 동결·커밋 → 조용한 창에서 전체 훑기 한 벌.**

까닭. 하네스를 고치면 harness 다이제스트가 움직여 지금까지의 봉투가 어차피 죽는다.
지금 훑기를 완주하고 그 뒤에 예산을 고치면 100분을 두 번 쓴다. §8.5가 스스로 세운
규칙(「고칠 것을 모아 두고 동결 뒤 한 번」)을 이번 구간에 그대로 적용한다.

**방향은 1번(진행 기반)이 본체고, 3번(붐비면 판정 안 함)은 분류에만 쓴다. 2번(기계
속도 보정)은 버린다** — 보정 그 자체가 부하를 타서 같은 문제를 한 층 위로 옮길 뿐이다.

고칠 자리를 넷으로 못 박는다. 이 밖은 안 건드린다.

| | 자리 | 지금 | 바꿀 것 |
|---|---|---|---|
| H1 | `drive.mjs` `goTo`·`stepOn` | 벽시계 900s·180s | 「진행 없음이 관측 N회 연속」으로 끝낸다. 진행 = 칸이 바뀜 · 맵이 바뀜 · 장면(대사·스크립트·배틀)이 열리거나 닫힘 · 남은 계획 길이가 줄어듦 중 하나. 관측 한 회는 기존 한 바퀴(≥330ms)라 기계가 느리면 저절로 늘어난다. 총 예산(`started + totalMs`)은 마지막 방어선으로 남기되, 그것에 걸렸는데 **직전에 진행이 있었으면** 판정은 FAIL이 아니라 「느림 · 관측 불능」이다 |
| H2 | `story.mjs` `pushBattle` | 45s(`--fight` 600s) | 진행 = 턴 번호나 배틀 로그 줄 수가 늚. 진행 없음 N회면 `stalled`, 끝나면 `ended`. 45초 상수는 지운다. gym3가 542번까지 갔다는 실측이 근거다 — 시간은 결함을 못 가른다 |
| H3 | `run.mjs` ㉙ · `journey.mjs` 첫 `page.goto` | 60s·180s | 가기 전에 개발 서버 뿌리를 맨 HTTP로 먼저 두드려 살아 있는지 본다. 그것이 안 오면 **BLOCKED(인프라)**로 적고 그 항목을 FAIL로 쓰지 않는다. `page.goto`의 값 자체는 안 올린다 |
| H4 | `journey.mjs` · `run.mjs` ㉖ · `evidence.mjs` | fps는 막힌 다리에서만 적힌다 | 5초마다 fps(`obs.perf()`)와 하네스 프로세스의 CPU 사용률(`os.cpus()` 시간 차)을 **판 전체에서** 표본으로 모아 봉투 `environment.load`에 요약(중앙값·p10·표본 수)으로 싣는다. 판정에는 안 쓴다 — 아래 분류와 §2.1에만 쓴다 |

**분류 규칙(3번의 자리).** 시간 모양의 실패(`deadline`·느림·인프라)만이 BLOCKED(경합)가
될 수 있고, 그것도 그 판의 `environment.load`가 붐빔(중앙값 fps < 15 또는 CPU 사용률
> 85%)을 가리킬 때뿐이다. **내용 모양의 실패는 절대 BLOCKED로 못 내려간다** — 대사
0/12쪽, 틀린 화면, 콘솔 오류, 표식 어긋남은 기계가 아무리 붐벼도 FAIL이다. BLOCKED는
통과가 아니고 그 묶음은 다시 돈다.

판정의 뜻이 바뀌므로 journey·e2e·story의 `contractVersion`을 올린다. 진행 계수기와
분류는 순수 함수로 떼어 시험을 붙인다(`observe.test.mjs`처럼). 하네스 수정은
`pnpm check`가 서면 커밋 하나로 동결한다.

## 3. 순서

1. **H1~H4 + §1.4.** `pnpm check` 통과. 커밋 하나. 이 지시서도 그 커밋에 넣는다.
2. **조용한 창.** 사용자가 「다른 작업을 껐다」고 말한 뒤에만 시작한다. 말하기 전에는
   `--only` 재현만 한다. 창은 최소 120분.
3. **전체 훑기 한 벌**, 이 차례로, 동시에 안 돌린다:
   `pnpm check` → `pnpm build` → `render:first` → `gpu:loss` → `journey` → `e2e` → `story`.
   앞 단계 성공을 뒤 단계 대신 세지 않는다. BLOCKED(경합·인프라)가 난 묶음은 그 묶음만
   다시 돈다. 내용 FAIL이 나면 훑기를 멈추고 첫 실패 경계를 보고한다 — 고치면 1로 돌아간다.
4. **§4 ①~③ 확인** 뒤 push:
   `git checkout master` → `git merge --ff-only hm-cutin-and-warp-fade` → `git push origin master` **한 번**.
   fast-forward가 안 되면 멈추고 보고한다(누가 master를 옮긴 것이다).
5. `pnpm verify:deploy https://radiant.siwon.it.kr/` → ⑯.
6. `pnpm e2e` 전체 **다시** 한 벌. ⑯만 따로 통과시킨 것은 e2e 통과가 아니다.
7. `pnpm release:check`. 열린 blocker가 ②(감수)뿐이어야 한다.
8. 배포 URL에서 이어하기 화면·필드·배틀 세 컷을 찍어 REPORT에 붙인다. `tools/shot`이
   URL을 못 받으면 그 사실을 적고 5·6의 결과로 대신한다.
9. 문서를 잰 값으로 갈아 끼운다 — `docs/DEPLOY.md` §1 표, `pnpm status`. 이력을 쓰지 않는다.
10. 사용자가 배포본을 직접 플레이한다. 그것은 구현자가 대신할 수 없다.

## §8 순서 변경 — 먼저 올리고, 새벽 창에서 한 벌 (2026-09-09 사용자 제안, 기획 승인)

사용자가 새벽 시간대를 오로지 이 검증에 내주기로 했다. 그 창을 한 번에 다 쓰기 위해 §3의 순서를 바꾼다: **push를 훑기 앞으로 옮긴다.** §3-2·§3-3·§4는 아래로 갈음한다.

먼저 사실 하나. journey·story는 배포 사이트에서 못 잰다 — `observe.mjs`의 dist 어댑터는 `/src`를 못 열어 값을 안 읽고, e2e는 로컬 dist를 스스로 띄운다. 그러므로 훑기의 CPU는 어차피 이 기계 것이고, 배포 사이트가 직접 재는 것은 ⑯·`verify:deploy`·마지막 세 장뿐이다. 이 변경이 사는 것은 CPU가 아니라 **창 하나**다 — 전에는 훑기 → 승인 → push → e2e 다시로 창이 둘 필요했다.

받아들이는 근거: 마지막 완주(붐빔 전, b2895f6)와 지금 사이의 src 변화는 `battleStore.ts` 한 파일(6a7d5fe)뿐이고, 그 자리는 `--only` 재현과 §1.4 전수로 확인됐다. 14fb963은 tools/·docs/만 건드려 dist가 안 바뀐다. 그래서 「안 잰 것을 올린다」의 폭이 좁다.
