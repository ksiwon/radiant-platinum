# 다음 지시 — 이야기 완료 조건과 잔여 복원 예외

작성 2026-09-08. OVERNIGHT_REPAIR_PLAN의 후속 지시다. 이미 확인한 설치와 경로 최적화를 처음부터 반복하지 않는다. 이번 목표는 오프닝→예진호수→첫 배지 정상 완주, door 화면 정상화, 최종 검증이다.

## 1. 검토에서 바로잡은 사실

- 현재 journey.json의 results는 9 PASS·8 FAIL(05~12)이다. REPORT의 12 PASS·5 FAIL은 실제 목록과 다르다. JSON을 기준으로 보고서 집계를 고친다. 결과 JSON을 보고서에 맞춰 바꾸지 않는다.
- 호수 장면 미완료는 유력한 가설이다. REPORT 본문은 막힌 순간 VAR_FOLLOWER_RIVAL_STATE를 아직 읽지 않았다고 명시한다. 115,852 좌표 일치만으로 활성 트리거를 확정하지 않는다.
- 경로 계획 병목 가설은 철회한다. 새 벤치마크와 실제 계획 시간은 수 초 가설을 지지하지 않는다. worker/A* 추가 개발을 하지 않는다. 이미 바꾼 정수 BFS의 정확성 검증은 유지한다.
- 설치 production에서 performance.measure 0회, dev 430회, 양쪽 오류 0은 그 동작 범위의 결과다. 이전 오류를 수정했다고 쓰지 않는다.
- story 확인 지점으로 엔딩을 본 것은 새 게임에서 엔딩까지 연속 진행했다는 증거가 아니다.
- Chrome 실행 기록은 --channel=chrome만 적혀 있다. headed가 실제 적용됐는지 실행기/로그로 확인하고, 확인 안 된 headed 성공을 주장하지 않는다.

## 2. 작업 A — 짧은 호수 재현부터 닫는다

`tools/e2e/drive.mjs`의 STOPS는 map 334의 (80,844)를 stepOn한 뒤 settle하고 다음 목적지로 간다. reached 판정은 `verdict === arrived && said !== false`라서 stood의 실패/warped와 이야기 완료를 반영하지 않는다. 이것은 명확한 관측 계약 누락이다.

1. 실패 직전 정상 세이브와 새 실행 디렉터리를 사용한다. 막힌 순간의 실제 맵·좌표·active script ID/PC·대사 상태·fieldScripts.vars.get(16518)를 읽어 기록한다. var=3이면 활성 조건을 지지한다. 4이면 다른 활성 이벤트·시점·콜스택을 추적한다. 실행 여부 표식 script=1을 원본 script ID 1로 혼동하지 않는다.
2. 원본 scripts_route_201.s와 scripts_lake_verity_low_water.s의 ScriptEntry, 워프, 좌표 이벤트, 종료 조건을 읽는다. 334→311/312 중 실제 분기와 필요한 접근 위치를 자료로 확정한다. 안쪽 맵 번호를 추측해 둘 다 무작정 방문하지 않는다.
3. 호수 진행을 명시적 단계로 만든다: 입구 접근→예상 워프→안쪽 준비→필요한 장면 시작→장면 종료→동행 상태 전이→정상 출구→동쪽 통행. `warped`는 전환 관측이며 단계 완료가 아니다.
4. 성공은 var 3→4의 관측과 스크립트/대사 종료, 정상 입력으로 다음 지역 통과를 함께 요구한다. 이미 더 진행된 저장에 대해 값을 4로 되돌리지 않는다. production에서는 /src import 대신 정상 UI·진행 결과를 사용하며 dev 진단용 읽기를 제품에 넣지 않는다.
5. 단계 실패 시 해당 단계를 실패로 남기고 뒤 구간의 무작정 시간 소모를 막는다. 새로운 BLOCKED 의미를 사용한다면 검사 계약·정본·보고에 명시한다. 기존 FAIL을 임의로 지우지 않는다.
6. 실제 호출부 회귀 검사: 입구 도착+warped만 발생한 경우, 장면 중단, 상태 3 유지는 완료가 아니어야 한다. 정상 장면 완료 후만 진행한다. 필수 이벤트 우회·변수 직접 쓰기는 금지한다.

완료: 짧은 재현에서 호수 장면 완료와 동쪽 통과를 확인한다. 이 성공만으로 체육관까지 해결됐다고 단정하지 않는다.

## 3. 작업 B — 오프닝의 예기치 않은 타이틀 이동

REPORT에 6판 중 3판이 타이틀로 돌아갔다는 기록이 있다. 전체 여정을 다시 시작하기 전에 이 시작 불안정을 조사한다.

- playOpening의 매 입력 직전에 현재 route와 의도한 화면을 다시 확인한다. /intro를 벗어난 뒤에는 입력을 보내지 않는다. /play는 성공, 예상 밖 /는 실패로 구분한다. 타이틀에서 Space로 새 게임을 다시 눌러 증거를 덮지 않는다.
- keydown/up, 클릭 대상, route 전이, resetSave 호출, navigation 호출 위치를 시간순으로 남긴다. 진단은 원본 호출을 보존한다. 관측 중 URL이 달라지는 경쟁을 피하도록 같은 표본에 시각/route를 묶는다.
- 실제로 누가 /로 보냈는지 찾는다. Escape를 안 보냈다는 사실만으로 제품/하네스 어느 쪽도 배제하지 않는다.
- 수정 뒤 fresh context 5판에서 /intro→/play, 새 게임 재초기화 없음, 입력 종료를 확인한다. 이 5판은 첫 화면 5판과 같은 전체 의미가 아니므로 별도 기록한다.

## 4. 작업 C — 복원 성공 외의 예외 경로 보완

`src/scene/restoreWorld.ts`의 arrive는 deps.settle(grid) 다음 markReady다. 현재 `deps.load(...).then(arrive, onRejected)`의 두 번째 인자는 load 거절만 받는다. arrive/settle이 던지는 예외는 여기서 실패 처리되지 않는다. 외부 matrix=0 경로는 동기 throw가 startRestore 밖으로 나간다. load 자체가 동기 throw하는 경우도 동일하다.

- 최신 세대의 load/settle 예외를 공통 실패 처리로 연결한다. 늦은 세대의 성공/실패는 현재 상태를 바꾸지 않는다. 외부 격자의 동기 완료 동작을 불필요하게 비동기로 바꾸지 않는다.
- settle이 실패하면 ready를 쓰지 말고 저장을 보존한 실패 UI를 유지한다. 부분 enter 후 재시도 시 이벤트 부작용을 중복시키는지 확인한다. 가능하면 실패 가능한 준비를 상태 반영 전에 끝내되, 확인되지 않은 전체 트랜잭션 재설계는 피한다.
- 기존 8개 소유권 검사에 load 동기 throw, 외부 settle throw, 비동기 load 성공 뒤 settle throw, 오래된 요청 실패를 추가한다. unhandled rejection 없이 failed로 가는 것을 검증한다.
- 이 검토는 N1 전체를 부정하지 않는다. 정상 복원 PASS와 세대 소유권 개선은 유지한다. journey 14 PASS 하나는 모든 실패 처리의 검증이 아니다.

## 6. 작업 E — 첫 배지와 최종 검사

하네스가 정상 진행했는데 전투에서 패배하면 정상 육성/회복/기술 선택으로 해결한다. 무한 재도전하지 않는다. 첫 배지 성공 이후 추가 정상 시작 1판으로 반복 가능성을 확인한다.

최종 소스/하네스로 render:first/gpu:loss/journey/story/e2e를 재실행하고 증거를 재생성한다. story --only=door는 전체 88자리 통과를 대신하지 않는다. 개별 npx vite build 성공은 pnpm build 경계까지 수행했다는 뜻이 아니다.
