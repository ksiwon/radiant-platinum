# 수정용 LLM 전달 프롬프트

`docs/orders/OVERNIGHT_RENDER_RECOVERY_PLAN.md`를 읽고 이번 야간 작업의 실행 지시서로 사용하라. 이전 지시서와 충돌하는 이번 잔여 작업 순서는 이 문서를 따른다. 계획만 설명하고 멈추지 말고 코드 수정·실험·검증·보고까지 진행하라.

목표는 정상 새 게임→첫 배지→저장·이어하기 동안 올바른 지형을 유지하고, 반복 전환 자원 증가와 간헐적 콘솔 오류를 해결하는 것이다. 현재 기준 보고는 HEAD 74acb3b, 이전 build 98ec47e이며 시작할 때 실제 신원을 다시 확인한다. 이전 build/봉투를 최신 합격으로 합산하지 않는다.

다음 순서로 실행하라.

1. 지시서 A: waitTerrain의 실제 false/true/오류/미완료 계약을 검증하고, 검은 칸 제외로 두 칸만 살아도 통과하는 시각 판정 허점을 막는다. 정상/실패 기존 컷에만 맞춘 문턱을 독립 검증이라 부르지 않는다. 합성 음성 대조는 항상 실행하고 실제 컷 누락은 미실행이다.
2. 지시서 B: stop-08의 요청→자료 읽기→decode/build→state→commit→render를 같은 request/batch ID로 추적한다. ChunkModels의 asked.current, pending.current, placed가 서로 다른 작업을 섞는지 먼저 검증한다. 실제 씬 UUID와 표식을 대조하기 전에는 “load가 끝내 안 끝났다”로 확정하지 않는다. 불변 batch 신원, 최신 세대 게시, 취소/throw/미게시 자원 정리, 공유 Promise 수명과 제한된 오류 복구를 실제 최초 실패 경계에 맞춰 수정한다.
3. 지시서 C: 기하 UUID의 생성 위치와 소유자를 찾는다. 예열 후 동일 경로 왕복에서 live 수와 생성/해제 잔액을 비교한다. 텍스처도 수정 후 증가가 남았으므로 함께 확인한다. 전역 dispose나 캐시 전체 삭제로 덮지 않는다.
4. 지시서 D: drift 관문은 보존하되 NaN, target/FOV, 렌더 카메라 상태를 검증한다. 2.4~8.5초의 카메라 이동이 사용자에게 노출되는지도 해결한다. 불연속 워프의 전환 시점 초기화와 로딩/페이드/입력 수명을 연결하고 일반 보행·스크립트/HM 카메라를 보존한다.
5. 지시서 E: performance.measure의 실제 실패 컴포넌트·prop/detail을 제한된 수집기로 특정한다. 원래 오류를 숨기지 않는다. 최종 설치된 production을 실제 자료와 전용 프로필로 검사하고 개발 결과와 구분한다.
6. 지시서 F: 최종 소스를 고정한 뒤 check/build, 짧은 재현, render:first, gpu:loss, 새 게임 전체 journey, e2e, story, 설치본 대조를 완료한다. 실패하면 첫 실패 경계를 보존하고 수정 후 필요한 증거를 갱신한다. 실제 수행하지 못한 종속 항목은 계약에 따라 구분하며 원시 JSON은 편집하지 않는다.

지속 실행 규칙:
- 사용자에게 통상적인 구현 선택을 묻지 말고 증거에 근거해 진행한다.
- 같은 가설에 45~60분 동안 새 정보가 없으면 다른 독립 경계로 조사 방법을 바꾼다. 목표 달성 전 임의로 완료 선언하지 않는다.
- 긴 검사 중 관련 파일을 바꾸지 않는다. GPU 실험을 동시에 실행하지 않는다. 전체/단계/개별 관측에 종료 가능한 상한을 둔다.
- 정상 첫 배지와 플래그 0, 저장 복원 수정은 보존한다. 게임 상태 주입·강제 회복·배지 지급·순간이동으로 최종 journey를 대신하지 않는다.
- 기존 자료·세이브·프로필·커밋을 보존한다. 추가 커밋·푸시·배포는 하지 않는다. 공개 CSP는 별도 blocker다.
- `.audit/runs/overnight-render-20260908/`에 실행 자취, 가설, 재현, 자원 표, 컷, 명령과 종료 코드, 증거 색인, REPORT 8절을 남긴다.

최종 답변에는 해결한 제품 결함과 검사자 결함을 구분하고, 최신 신원별 PASS/FAIL/BLOCKED/미실행, 남은 문제, 보고서 경로를 적어라. “개선”·“이번 실행 무오류”·“원인 해결”을 서로 바꿔 쓰지 마라.
