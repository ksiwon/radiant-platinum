## 2. 확정 문제와 수정 티켓

### R1 — P1: 배틀 재생기와 3D 연출의 시계가 다르다

위치: `src/ui/battle/useBattlePlayback.ts:41,172,197`, `src/scene/battle/MoveVfx.tsx:158`, `src/scene/battle/BattleStage.tsx:391`, `src/scene/battle/BattleBallEffects.tsx:126`.

재생기는 requestAnimationFrame 콜백마다 `r.wait--`한다. VFX와 몸은 delta 초, 공은 performance.now 초를 사용한다. 원작 60프레임을 디스플레이 60회와 동일시한 구현이다.

**코드 재현:** 실제 useBattlePlayback 소스를 TypeScript transpile 후 React hook과 RAF를 제어해, text=null인 120프레임 move 뒤 damage를 배치했다.

| RAF 주기 | 기준 연출 시간 | 피해 이벤트까지 실제 경과 |
|---|---:|---:|
| 30Hz | 2,000ms | 4,033ms |
| 60Hz | 2,000ms | 2,017ms |
| 120Hz | 2,000ms | 1,008ms |
| 144Hz | 2,000ms | 840ms |

재현: `node .audit/review-20260919-playback-clock.mjs`. 결과 JSON은 같은 이름이다. 이 값은 합성 RAF 재현이며 실제 144Hz 디스플레이 녹화 값은 아니다. 하지만 실제 함수가 refresh rate에 종속되는 것은 확인됐다.

수정 계약:

1. 프레임 수는 콘텐츠 데이터로 유지하되 실행은 공통 배틀 시계의 ms 또는 누적 60Hz 고정 step으로 바꾼다. 모니터 Hz를 추정해 상수를 보정하지 않는다.
2. 메시지 대기, HP gauge, 몸 동작, VFX, 공, 카메라를 동일한 시작 시각/진행률로 묶는다. `BattlePresentationClock` 같은 엔진 독립 모듈과 UI/씬 어댑터로 구현할 수 있다. UI가 scene 모듈을 import하는 역의존은 피한다.
3. 탭 숨김/복귀와 긴 프레임에서 여러 의미 있는 박자가 한 번에 소모되지 않게 한다. 연출 중 일시 중단 정책을 하나로 정하고 performance.now 기반 공에도 적용한다. 숨긴 동안 결과만 진행해 복귀 시 마지막 장면만 뜨면 안 된다.
4. 효과마다 seq와 start/complete 상태를 가진다. 완료 acknowledgement 또는 동일 timeline 종료를 기다린다. 모델 누락·실패는 명시적 fallback 완료 경로를 갖추고 무한 대기하지 않는다. timeout을 성공으로 위장하지 않는다.
5. `MoveVfx`의 `Shape`는 새 shot이 도중에 오면 useRef(t)가 재사용될 수 있다. 효과별 key/리셋과 오래된 done callback 차단을 넣는다. 이전 효과의 종료가 새 효과를 지우지 않게 한다.

검증: 30/60/120/144Hz 및 불규칙 frame timestamp에서 순서와 소요 시간이 같아야 한다(한 frame 수준 오차 허용). 이동/VFX 종료 전 HP가 바뀌지 않아야 한다. 배틀 속도 전 설정, A/Z 연타, 백그라운드 복귀를 포함한다. 실제 브라우저와 fake clock 결과를 별도로 제출한다.

### R2 — P1: 포획 결과 글이 공 연출을 기다리지 않는다

위치: `src/engine/battle/playback.ts` default 분기(`show([told],0)`), `src/ui/battle/messages.ts:660`, `BattleBallEffects.tsx`, `battleBallMotion.ts`.

ball 전용 박자가 없어 **ball 이벤트/hold0 → 포획 결과 문구/hold30**가 생성된다. 재생기는 hold0을 같은 RAF 안에서 이어 처리한다. 결과는 던지기·봉합·흔들기와 동시에 알려진다. 3회 흔들기 결과 시점은 현재 공 함수 기준 `0.92 + 3×0.46 = 2.30초`다.

**코드 재현:** `node .audit/review-20260919-capture-order.mjs`가 실제 buildBeats에서 위 배열을 출력한다. view helper는 stub이며 순서 검증용이다. 실제 포획 영상 재현은 별도 완료 조건이다.

- ball 전용 분기로 **던짐 → 대상 수납 → 흔들기 0~3회 → 성공/탈출 확정 시각 → 결과 글 → 다음 행동/배틀 종료**를 만든다. 메시지 문자열 길이를 공 대기 시간으로 사용하지 않는다.

시험: 0/1/2/3회 실패, 3회 성공, 보장 포획, 사파리, 가방 수량 감소 1회. 자동 진행과 연타 둘 다 검사하고 결과 문구 최초 시각이 결과 확정 시각 이상인지 타임라인으로 assert한다.

### R3 — P1: HP 감소와 기절 표현을 분리해야 한다

위치: `BattleStage.tsx:244,399,488`, `engine/battle/view.ts:239,277`, `engine/battle/playback.ts:242`.

현재 damage 이벤트가 hp=0을 적용하자마자 Slot은 `mon.hp<=0`으로 사라지기 시작한다. gauge는 holdMs 동안 CSS 전환을 하므로 HP가 내려가는 도중 몸이 사라질 수 있다. 별도 faint 이벤트를 기다리지 않는다. fade 중 `t<0.99`이면 motion이 `enter`로 선택되어 퇴장에도 등장 클립이 선택되는 구조다. faint 박자는 7프레임뿐이며 몸 fade는 0.35초다. **코드로 확인한 상태 결합 문제**이고 이번 실제 KO 연속 영상은 미검증이다.

수정 계약:

- 숫자 HP 목표와 화면상의 `alive/fainting/hidden` 상태를 분리한다. 피해 HP가 0이어도 gauge 완료 전에는 살아 있는 모습/피격 표현을 유지한다.
- 명시적인 faint presentation 이벤트로 기절 시작 → 완료 → 기절 글 → 경험치/교체를 연결한다. 이미 view의 fainted가 damage에서 true가 되므로 해당 boolean으로 갈아 끼우는 것만으로는 해결되지 않는다.
- 적절한 원본 faint clip이 없으면 명시적인 가라앉기/fade fallback을 사용한다. enter clip을 퇴장에 재사용하지 않는다. 상대와 내 포켓몬, 더블의 slot별 처리를 분리한다.
- `HOLD_FAINT=7`은 체력창 퇴장 값이라는 주석이 있다. 이를 몸 동작 완료 시간으로 취급하지 않는다. 엔진의 실제 전투 결과/기절 판정을 늦추지 말고 표시 순서만 제어한다.

완료: 큰 HP 감소 KO·독/화상 KO·반동/동시 KO·더블 한쪽 KO에서 gauge 종료 뒤 기절 시작, 모델 제거 뒤 교체가 순서대로 한 번만 일어나야 한다.

### R4 — P3: Scale2x가 미러 반복 경계를 일반 반복으로 읽는다

위치: `src/scene/chunkMesh.ts:390~462`.

sliceTexture는 wrap mode가 Clamp가 아니면 boolean true를 넘긴다. scale2x는 true이면 modulo로 반대쪽 끝 픽셀을 읽는다. 따라서 `MirroredRepeatWrapping`도 Repeat와 같아진다. 미러 경계의 바로 바깥 이웃은 반대편 끝이 아니라 경계 픽셀이어야 한다.

**코드 재현:** 실제 scale2x 함수에 불투명 4×4 경계 fixture를 넣었을 때 출력 (0,2)의 red가 2, 올바른 미러 경계에서는 1이다. `.audit/review-20260919-mirror.mjs/json` 참조. 추가로 현재 추출된 chunks/props/distortionProps/starter의 PT3C 1,301파일을 조사했으며 활성 미러 반복 재질은 0개였다(`.audit/review-20260919-mirror-usage.json`). 따라서 현재 화면 결함의 원인으로 확정하지 않는다. 합성 입력에서 확인한 지원 경로의 잠재 오류이므로 우선순위는 P3로 낮춘다.

수정: bool 대신 `clamp/repeat/mirror`를 축별 전달한다. mirror 좌표는 길이 2N 주기로 정규화한 뒤 N 이상이면 `2N-1-q`로 반사한다. 매 확대 단계에도 동일 모드를 유지한다. GPU texture.wrapS/T와 CPU 이웃 샘플의 의미를 일치시킨다. 음수·N·2N 경계, X/Y 독립, 투명 텍셀, 2회 확대를 시험한다. 실제 rep 미러 비트 자산을 골라 1·3인칭 이음 확대 캡처를 남긴다.

- **기존 진단 미해결:** 실내 틈/깨어진 세계 광선 결과는 `docs/DEPLOY.md §5.2`와 최신 FP 기록을 대조해야 한다. 오래된 전체 개수를 현재 결함 개수로 반복하지 않는다. 광선이 허공을 만났다는 이유만으로 열린 지역에 벽을 세우지 않는다.

구현 지시:

1. 실제 렌더에 쓰는 camera의 world/projection matrix로 픽셀을 역추적하고 삼각형 hit barycentric UV, material, 원본 sourceKey를 기록한다. 재구성 카메라와 잘못된 UV 중심값은 사용하지 않는다. 투명도·후처리 때문에 첫 ray hit와 화면색이 다를 수 있으므로 메시별 숨김 비교/오브젝트 ID 진단도 사용한다.
2. 센터는 입장 직후뿐 아니라 정상 보행으로 같은 칸에 접근·회전·퇴장해 보이는 범위를 확인한다. 플레이 가능 상태와 진단 워프 위치를 구분한다. 문/프레임 geometry와 벽 UV를 역할별로 나누고 인접한 실제 벽의 texel 밀도를 유지한다. 벽 전체에 문 무늬를 늘려 붙이거나, 화면을 숨기려 카메라 방향을 강제하지 않는다.
3. 동굴은 가해 mesh를 확정한 뒤 해당 면/소유권/깊이/UV를 고친다. 흰색만 다른 색으로 덮거나 전체 DoubleSide를 켜서 끝내지 않는다.
4. 양 backend, 0.5/1/2타일, 8방위, 1↔3 전환 및 실제 출입을 검증한다. 가까운 벽을 보는 장면 자체는 허용 가능하나 무엇을 보는지 식별할 수 있고 틈/무출력과 구별돼야 한다.

### R6 — P2: 전체 명세와 ‘네 건 완료’의 범위를 다시 맞춘다

현재 구현 기록의 2026-09-18 표는 자홍·볼라드·갈색 턱·카드 분류의 네 건을 말한다. 전체 명세의 아래 항목은 별도다.

| 원래 계약 | 현재 확인한 코드 | 후속 처리 |
|---|---|---|
| 나무의 검수된 수관/줄기 변형, 실제 bounds와 LOD | Foliage는 Icosahedron/Octahedron 덩어리, ballNormals, 고정 TREE_SPHERE=1.35 | §6.4/§10 대조. 실제 자연스러움과 culling/LOD를 재검수하거나 구현. 단순 다면체 사용 자체를 결함으로 단정하지 않되 완료 근거 필요 |
| 바위의 의미별 비대칭 형태·면 법선·텍스처 | Rocks는 Icosahedron+ballNormals와 높이별 평균 색 띠 | §6.3의 최종 목표와 차이. 대표 바위 앞·옆·위 close-up 및 의미별 recipe로 처리 |
| 수면의 층/연결 영역 구분·해안 감쇠 | 물 칸 네 개 최소 높이, x*4096+z 공유, LIFT=.09; 해안 감쇠 없음 | 기존 파고 관통 수정은 인정. 다른 높이 수면의 인접/중첩 및 기슭 상승을 별도 검사. 근거 없는 ‘전 수면 완료’ 금지 |
| 카드 전체의 의미별 최종 판정 | 카드 후보표 미검수0과 coverage의 unreviewed는 서로 다른 집계 | 후보표와 전체 sourceParts 모집단을 구분한 coverage 보고 필요 |

이번에 읽은 `.audit/first-person/coverage.json`은 2026-09-18 생성이며 sourceParts 284,314, verified 1,636, unreviewed 282,678이다. **282,678개 결함이라는 뜻이 아니다.** 일반 원본 면도 포함한다. 반대로 좁힌 후보표 미검수0으로 모든 원재료가 검수됐다고 주장할 수도 없다.

수정 LLM은 전체 명세 §6~10 각 항목을 `구현됨/의도적 유지/검증대기/미구현`으로 매핑하고 이유와 현재 evidence를 남긴다. 의도적인 평면 장식은 유지해도 된다. 나무/바위를 한꺼번에 다시 만들기 전에 현재 화면과 기존 목표의 차이를 대표 자산으로 입증하고, 필요한 종류만 수정한다. 물은 같은 높이/층/연결 영역에서만 공유하고 해안에 밀착해야 한다. 임의로 전체 lift를 더 올려 해결하지 않는다.

Scale2x 64 목표는 새 원본 디테일을 복원하지 않는다. 원본에 64×64가 있다는 사실도 world texel density가 같다는 근거가 아니다. 현재 정책은 실용적인 확대 선택으로 기술하고, x2/x4의 정적 품질·장면 전환 누적 메모리를 비교해 결정한다.

## 4. 수정 순서와 공통 설계

실행 순서: **R1 공통 시계 → R2 포획/등판 대기 → R3 HP/기절 → R5 공간 결함 → R6 전체 범위 마감 → R4 mirror 잠재 오류 → 최종 회귀**.

R1~R3은 한 presentation 계약으로 설계하되 리뷰 가능한 변경 단위로 나눈다. battle controller가 확정한 사건 순서는 보존한다. 글과 시각 효과를 나타내는 Beat에 명시적인 완료 조건을 추가하고, 전투 중 새 이벤트가 붙어도 이미 재생한 prefix가 달라지지 않는 기존 불변식을 유지한다. 상대/내 쪽/더블 slot을 seq와 함께 식별한다. 폴백 자산과 네트워크 지연도 완료 조건의 일부다.

기존 폼 변화는 protocol/view에 구현되어 있다. BattleStage의 ‘formechange가 뷰에 안 올라온다’ 주석만 보고 기능 미구현으로 되돌리지 않는다. 주석과 최신 구현을 대조하고 낡은 설명은 정리한다.

## 5. 필수 통합 회귀와 완료 기준

### 5.1 배틀 순서표

모든 기술을 사람 눈으로 한 번씩 봤다는 근거가 없으면 ‘배틀 모션 전부 완료’라고 보고하지 않는다. 전체 지원 기술은 자동 timing/source coverage를 만들고, 의미가 다른 연출군은 실제 영상으로 검증한다.

| 장면 | 최소 검증 |
|---|---|
| 야생/트레이너/더블 등장 | 배경 준비 → 등장 → 볼 열림 → 몸 → 메뉴; 내/상대 순서, preload 실패 |
| 물리·특수·상태·자기 강화 | 기술 글 → 몸/VFX → 피격 → HP → 급소/상성/부가 글 |
| 연속 공격·광역·빗나감·무효 | 타수별 HP/반응, 올바른 slot, 빗나간 대상에 피격 금지 |
| 충전/공중날기/구멍파기 | 사라짐과 복귀, 다음 턴까지 남아야 하는 상태 |
| 교체·강제교체·기절 | 회수/퇴장 완료 → 새 공 → 새 몸; 오래된 clip/VFX 초기화 |
| 포획 성공/실패·사파리 | R2 전 사례, 결과 뒤 UI·저장·다음 턴 |
| 날씨·독·반동·동시 KO | 메시지/게이지/기절/승패 순서, 더블 양쪽 처리 |
| 경험치·레벨·기술·진화 | 배틀 종료와 파티 HP/폼/기술 일치, 선택 중 멈춤 |

30/60/120/144Hz 논리 시뮬레이션과 실제 WebGL/WebGPU 대표 영상을 별도로 제공한다. auto/A연타/배틀 속도 전 설정을 확인한다. 이벤트 seq, beat index, logical time, VFX begin/end, HP begin/end, 메시지 최초 표시, sceneReady, 전투 phase를 하나의 trace에 담는다. trace assertion으로 확인한 순서와 사람이 확인한 화면을 구분한다.

### 5.2 시점 및 게임 진행

- 1→3→1 반복 20회: 위치·높이·yaw/pitch 정책·자기 몸 visibility·입력 기준 복원, 포인터 잠금과 메뉴 닫기.
- 문 출입/워프·계단·갈색 턱 세 방향·자전거·surf·낚시·동굴·깨어진 세계: 양 시점 이동과 토글. collision과 화면 mesh를 따로 확인.
- 1인칭에서 전투 진입 → 기술/포획/승리/도주/전멸 → 필드 복귀 시 원래 옵션·카메라·플레이어 visibility 복원. 별도 3인칭 시작 판도 실행.
- 저장/불러오기, provider 교체, 맵 왕복 10회에서 stale geometry·재질 누락·메모리 누적·빈 인스턴스 draw 확인.
- 기록용 journey는 shortcuts=[]인 새 게임과 고정 source/harness/data digest로 실행. 좋은상처약 미표시 진단도 수집. 이번 짧은 확인 지점 검사가 journey 완주를 대신하지 않는다.

### 5.3 증거 유효성

**직접 실행:** `pnpm release:check`는 종료 코드 1이다(`.audit/review-20260919-release.log`). 이번 최신 판정의 blocker는 **1건: journey가 검사한 source digest `5c3bdc731327`과 현재 `c652443121e4`가 다름**이다. 검사 초기에 읽은 이전 release-blockers 파일에는 여러 건이 있었으나 이번 판정 결과로 갱신해 읽는다. blocker 문구는 아직 첫 배지라고 하지만 실제 journey 계약은 둘째 배지까지 확장되어 있으므로 현재 정본 roster 전체를 재실행해야 한다. 이는 현재 게임이 실제로 완주에 실패했다는 뜻이 아니라 최신 코드의 유효한 완주 증거가 없다는 뜻이다. 최종 수정 후 판정기를 다시 실행한다.

최종 결과는 다음을 모두 제공해야 한다: 고정 commit/source/harness/data/build ID, check 결과와 skipped 이유, 두 backend 확인, 영상/trace/이미지 경로, 전체 scope coverage 및 예외. 진단 판을 배포 성공으로 옮기지 않는다. 한 색/자홍/오류 수치만 낮추거나 검사 threshold를 느슨하게 해 완료 처리하지 않는다. 통행 가능한 시점의 품질 결함과 진단 전용 위치의 관찰을 구분한다.

## 6. 수정 LLM에게 전달할 요약 지시

이 문서의 R1~R6을 순서대로 처리하라. 시작 전에 현재 HEAD와 작업 트리를 기록하고 다른 작업을 보존하라. 진단용 `.audit` 파일이 없더라도 이 문서의 재현 조건으로 테스트를 재작성할 수 있어야 한다. 먼저 R1~R3을 함께 설명하는 공통 presentation timeline을 설계하되 실제 사건 계산은 변경하지 말라. 실제 source를 사용하는 실패 테스트를 만든 뒤 수정하고, 의미 있는 경계/순서 검증을 수행하라. 정적 통과와 실제 플레이 통과를 구분하고 미실행은 미실행으로 남겨라. 마지막에는 네 건 개선 완료가 아니라 전체 명세의 coverage와 미해결 항목을 보고하라.
