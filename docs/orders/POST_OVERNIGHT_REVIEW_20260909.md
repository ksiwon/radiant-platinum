# 야간 결과 후속 검토 및 실행 지시 — 2026-09-09

이 문서는 OVERNIGHT_RENDER_RECOVERY_PLAN.md의 후속 우선순위를 정한다. 이전 계획의 자료 보존·정상 입력·신원 검증 원칙은 유지한다. 검토는 REPORT.md, 현재 diff, drive/route 및 자원 수명 코드를 근거로 했다. 제한 검사 3파일 30개가 통과했다. 긴 게임 실행과 컷 육안 검토는 이번 검토에서 수행하지 않았다.

## 1. 받아들일 성과와 아직 닫지 않을 항목

- LandBatch로 땅·신원·재질을 함께 게시한 방향은 맞다. 이것이 stop-08의 실증된 원인이라고 확대하지 않는다.
- snap의 위치·시선 초기화와 target을 포함한 drift는 타당하다. 목적지 room bounds가 늦게 바뀌는 경우와 스크립트 카메라는 별도 확인한다.
- 공통 format Promise의 reject 후 재시도 가능화, 캐시 삭제 시 Promise 신원 확인은 유지한다. 실제 화면이 자동 복구되는지는 별개다.
- WeakMap 재사용은 생성량을 줄였지만 GPU 자원의 명시적인 수명 관리를 대체하지 않는다. 현재 +11/왕복은 미해결이다.
- story 88 PASS는 해당 신원의 장면 검사 성과다. 최신 정상 여정 첫 배지와 배포본 ㉖의 실패를 대신하지 않는다.
- 설치본 짧은 시나리오의 measure 호출 0회는 그 실행의 관측이다. 코드의 production 분기 분석과 구분해 기록하고 호출 0회만을 “구조적 불가능”으로 표현하지 않는다.

## 2. 우선순위

P0 배포 하네스 계약 수정 → P0 경로/입력의 최초 실패 재현 → P1 기하 수명과 배치 실패 정리 → P1 전환/오류 회복 검증 → 최종 검사 갱신.

기존 PASS 보존 때문에 알려진 결함을 남기는 방침은 폐기한다. 이전 봉투는 이력으로 보존하고 새 수정으로 무효가 되면 그대로 둔 뒤 재실행한다. 증거가 일시적으로 줄어드는 것은 수정 중 정상적인 상태다. 증거 검증 규칙을 약화해 재검사를 피하지 않는다.

## 3. 배포본 ㉖ — 개발 전용 관측을 공유 드라이버에서 분리

drive.mjs의 lakeVars/snapshot은 /src 동적 import에 의존하고, pickMove도 import 실패를 null로 삼킨다. 한 함수만 catch하면 실행은 이어져도 관측과 행동이 달라질 수 있다. 파일 전체의 개발 소스 의존성을 먼저 목록화한다.

개발용 관측 어댑터와 배포용 관측 어댑터를 명시적으로 선택한다. 드라이버는 공통 읽기 계약을 사용하고, 관측 불가는 false/0/성공과 다른 상태로 반환한다. 배포 서버에는 /src 요청 자체를 보내지 않는다.

배포에서 사용할 수 있는 근거는 정상 UI, 이미 배포되는 읽기 전용 표식, 정상 내보내기 세이브 등이다. 새로운 공개 쓰기 API나 진행 상태 주입은 만들지 않는다. 읽기 전용 표식을 추가해야 한다면 노출 범위와 버전을 작게 정한다.

호수 완료를 단지 방문 map 목록으로 대신하지 않는다. 이전에 “안쪽 입장 ≠ 장면 완료”가 실제 결함이었다. 순서 있는 전환·대사 종료·후속 정상 입력에 의한 동쪽 통행 등 완료를 구분하는 근거를 정의한다. 필요한 의미를 증명하지 못하면 관측 불가로 남긴다. 약한 근거로 같은 검사의 PASS를 만들지 않는다.

회귀 검사: 개발 서버와 dist 각각 드라이버가 동작, 배포에서 /src 요청 0, 관측 불가가 PASS 아님, 호수 입장만 하고 완료 전 중단하면 거절, 완료 후 정상 통행 인정. pickMove의 fallback 기술 선택도 경로별 동작을 기록한다.

먼저 ㉖만 짧게 재검증한 후 공유 변경이 끝난 시점에 전체 e2e/story/journey를 갱신한다.

## 4. 길 찾기 — 46% 전체 통계로 원인 확정 금지

planned()는 /풀회피 시도와 일반 시도, 경유 후보를 한데 센다. 풀회피 unreachable 뒤 일반 경로 found는 실패한 여행이 아니다. 세 실행의 하네스와 방문 구간도 다르므로 23%→46%는 동등 조건 비교가 아니다. “세 판 차이는 운” 역시 미확정으로 정정한다.

### 4.1 목적지 하나 단위의 기록

episode ID마다 시작 map/matrix/정수좌표·원시좌표, 목적지 종류(구역/문/밟기/NPC 접근), 목표 좌표 집합 또는 재구성 가능한 spec, 데이터 지문, avoid/shun/grass 정책, 배틀·대화·스크립트 상태를 남긴다.

한 episode에 풀회피 결과, 일반 결과, mapRoute 후보, 선택 경로, 다음 입력, 실제 이동, 종료 이유를 연결한다. 요약은 다음으로 분리한다:
풀회피 실패 후 일반 성공 / 모든 일반 후보 unreachable / budget / invalid / 경로 found 후 이동 실패 / 도착 후 대화 실패.

현재 planSummary는 느린 계획만 상세를 남긴다. 이번에는 빠르게 실패한 계획이 중요하므로 실패 episode를 제한된 JSONL에 남긴다. 같은 요청을 계속 중복 저장하지 않고 반복 횟수와 첫/마지막 상태를 기록한다.

### 4.2 정적 목표 예외의 적용 범위

route.mjs의 planPath는 blocked 또는 avoid인 다음 칸도 isGoal이면 허용한다. 목표 predicate가 특정 문일 때의 예외가 구역 전체·NPC 접근·일반 타일에도 적용된다.

실패 경로의 끝점이 통행 불가/피해야 하는 warp/잘못된 높이인지 먼저 확인한다. 재현되면 목표 종류에 따라 문 진입 예외를 명시적으로 전달하고 일반 구역 목표는 실제 진입 가능한 칸만 인정한다. 문 입장 자체를 전부 막는 수정은 하지 않는다. 이 경계를 실제 제품의 이동 규칙과 대조한다.

### 4.3 상태 구분이 호출부까지 남는지

planPath는 budget와 unreachable을 구분하지만 drive의 path helper는 최종 plain.keys만 반환한다. 상위 goTo는 null을 같게 다루며 mapRoute 전환·lost 누적을 한다. stepOn도 keys만 읽는다. 상태 구분을 만들었다는 보고와 실제 상위 동작을 일치시킨다. budget를 길 없음으로 단정하거나 invalid를 반복 탐색하지 않는다.

### 4.4 최초 입력 실패를 잡는다

광대 ② 실패 직전 또는 집으로 돌아가지 못한 짧은 구간 하나를 선정한다. 정상 진행으로 만든 세이브 복사본에서 같은 구간만 실행한다. 최종 검사는 새 게임이지만 진단은 전체 여정을 반복하지 않는다.

plan found 후 실제 이동 실패라면 첫 어긋난 한 걸음의 expected/actual tile, 방향키 down/up, 프레임 진행, 잠금, 전투/대화/전환, 지형 높이·거동, warp/trigger를 기록한다. 경로 없음을 입력 실패와 섞지 않는다. NPC 접근은 runtime 자리 재조회와 계산대 도달·마주 보는 방향·대화 개시를 각각 기록한다.

shun에 어떤 실패를 어떤 수명으로 넣는지 확인한다. 대화/야생 전투로 못 움직인 칸을 영구 장애물로 만들지 않는다. 되밀리는 스토리 관문은 충돌 타일로 고치지 않고 선행 조건을 정상 진행한다. 야생 22회가 왜 생겼는지 경로 반복인지 필수 풀 구간인지 나눈다.

원인을 찾기 전 예산을 더 늘리거나 무조건 회복·우회 기능을 추가하지 않는다. 목적지 episode 단위로 동일 정상 세이브의 재현을 3회 성공시킨 뒤 새 게임 전체 여정을 돌린다. 난수 고정 진단을 쓰면 별도 표기하고 최종 여정 증거에 합산하지 않는다.

## 5. 남은 기하 — WeakMap과 dispose의 역할을 분리

splitShadow의 원본과 파생 기하는 attribute/index를 공유한다. “원본이 GC되면 GPU도 정리된다”는 주장은 하지 않는다. three의 renderer 등록과 dispose 이벤트 수명을 추적한다.

원본 UUID→solid/soft UUID→사용 중 mesh→배치/캐시 owner를 연결한다. 원본이 배치 전용(p.merged 등)인 경우 원본과 파생 묶음이 마지막 사용 후 모두 해제되는 설계가 필요하다. 살아 있는 공유 원본을 파생 기하 dispose로 손상시키지 않도록 수명을 묶는다.

선택지는 실제 backend 구현을 확인해 결정한다: 마지막 사용 뒤 전체 묶음 해제, 공유 속성 참조 계수, 독립 attribute 복제의 비용이 합리적인 경우 독립 소유. “공유이므로 영원히 해제 불가”로 남기지 않는다. WebGPU와 WebGL의 내부 자원 처리 차이를 확인하고 둘 다 재사용 장면을 검사한다.

cache key는 shadow mask만 사용한다. 원본 groups/index/attribute가 변하지 않는다는 전제가 맞는지 확인하고, 변경 가능한 원본이면 invalidation 또는 버전을 둔다. 필요 없는 추상화를 만들지 말고 실제 호출부의 불변성을 검증한다.

예열 후 같은 자료 집합 왕복 20회 이상, 동일 map 위치에서 geometry/texture 현재 수와 생성·해제 잔액이 안정되는지 확인한다. 전환당 5~6개 증가가 남으면 완료가 아니다. GPU 업로드 안 된 중간 JS 객체의 생성 수를 GPU 누수와 섞지 않는다.

## 6. LandBatch의 나머지 수명 계약

현재 mats cache와 next는 then 내부에 생성된다. 구성 중 예외가 나면 catch는 빈 batch를 게시하지만, 그때까지 만든 재질/조각 텍스처/합성 기하를 해제하는 경로가 보이지 않는다. 부분 생성 후 throw를 주입해 먼저 재현한다.

배치 생성용 소유 자원 목록을 실패 정리 경계에서 접근 가능하게 하고 commit으로 소유권이 이전되기 전에는 실패/취소가 정리하도록 한다. state 제출 뒤 커밋되지 않고 대체되거나 언마운트되는 경우도 확인한다. 공유 cache 자원은 이 목록에서 제외한다.

LandBatch 바깥의 cameraSystem.rooms 갱신, foliage/rocks/grass/water 상태도 실제 땅과 불일치할 수 있는 시점을 검사한다. 꼭 필요한 동기 상태만 같은 batch로 묶거나 commit 경계로 옮긴다.

새 format 요청을 허용하는 것은 자동 재시도가 아니다. effect 의존성이 그대로인 실패 상태에서 사용자가 어떻게 회복하는지 확인한다. 제한된 재시도/오류 UI가 없다면 여전히 미구현으로 남는다. Promise 미완료·실패·오래된 응답은 각각 종료 가능한 경로가 필요하다.

제품 회귀 검사는 지연 순서 역전, 같은 행렬 존 변경, build 중 throw, 제출 후 언마운트, 첫 format reject 뒤 재요청 성공, 공유 자원 재사용, snap 후 일반 보행 보간을 포함한다. 기존 chunkMesh 검사는 기본 분할 의미를 검사하지만 새 캐시·실패 수명 계약의 증거를 대체하지 않는다.

## 7. 진단기가 새 문제를 만들지 않도록

perfSpy는 catch 안에서 structuredClone(detail)과 자식 clone을 반복하고 Object.entries로 값을 읽는다. 이는 큰 객체를 실제로 복제할 수 있으며 getter/proxy 예외가 원래 오류를 덮을 수 있다. 깊이·개수 제한만으로 비용이 제한되지 않는다.

원래 오류는 진단 실패와 무관하게 그대로 재전파하도록 별도 try/catch/finally 경계를 둔다. 첫 실패의 bounded key/type/prop 이름을 우선 남기고, 무거운 clone 분해는 작은 재현에서 수행한다. 부분 자식 목록만 확인하고 “객체 자체가 범인”이라고 확정하지 말고 미검사 범위를 표시한다.

waitTerrain의 Promise.race는 evaluate를 취소하지 않는다. timeout마다 새 관측을 누적시키지 말고, 해당 관측 timeout을 명시적 진단 실패로 종료하거나 하나의 in-flight 작업만 유지한다. 페이지 자체를 닫아 정리해야 하면 실패 컷/이전 trace 보존 후 검사 전용 페이지에서만 한다. 새 유한 상한 검사에 최대 동시 evaluate 수와 원래 오류 보존도 포함한다.

stop-08 trace는 현재 sheet/chunks 전체 완료 위주다. 모든 자료 중 하나가 멎으면 어떤 key인지 못 안다. 하위 리소스 시작/끝/실패의 제한된 목록 또는 미완료 key 요약을 남기고 cleanup 때 superseded를 즉시 기록한다. 무거운 추적은 진단 모드에 한정한다.

## 8. 최종 순서와 보고

1. 배포 어댑터와 경로 최초 실패 재현을 고친다.
2. 기하·배치 실패 정리·진단기 오류 보존을 마무리한다.
3. 변경된 경계의 회귀 및 짧은 재현을 수행한다.
4. 소스·하네스·자료·배포물·계약을 고정하고 check/build 및 최종 검사를 갱신한다.
5. 정상 새 게임 journey 첫 배지·저장·복원과 대표 장면, 배포 ㉖, story 전체, e2e 전체, render:first/backend 및 gpu:loss를 기록한다. 설치본 긴 경로의 범위를 명시한다.

새 검사 계약의 종속 항목은 원인 FAIL과 미실행/BLOCKED를 구분한다. 기존 원시 결과는 수정하지 않는다. 공개 CSP는 별도다. 커밋·푸시·배포는 하지 않는다.

납품은 `.audit/post-overnight-20260909/`에 보고·경로 episodes·자원 수명·회귀 결과·원시 로그 색인을 남긴다. 같은 가설 반복 대신 최초 어긋남을 좁히며, 통상적인 선택을 사용자에게 다시 묻지 않고 진행한다. 미해결을 숨기지 않되 “기존 PASS 보존”을 이유로 필요한 수정을 미루지 않는다.
