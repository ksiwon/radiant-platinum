## 2. 우선 수정 A — HP 감소 중 입력으로 기절이 앞당겨짐 (P1, R3 재개)

### 원인과 재현

`src/engine/battle/playback.ts:260`의 `show([marked], drainFor(e))`는 damage/heal 박자를 입력으로 건너뛸 수 있게 만든다. `src/ui/battle/beatRunner.ts`의 `advance()`는 presentation이 아닌 박자의 holdLeft를 0으로 만든다. `BattleScreen.tsx:360`은 재생 중 confirm/cancel을 이 함수에 연결하며 메시지 영역 클릭도 같은 함수다.

정상 초기 HP 20/20에서 0/20으로 감소시키는 실제 박자는 48프레임이다. scale=1에서 HP 전환 800ms가 요청되지만, 직후 advance를 한 번 호출하면 다음 60Hz 걸음(16.67ms)에 faint 사건이 접힌다. 입력이 없으면 816.67ms에 접힌다(부동소수/걸음 단위 오차 포함). 앞선 단순 fallback 진단의 500ms도 같은 결함이지만 최종 증거 파일은 정상 초기 상태의 800ms 표본이다.

HP 표시 자체는 `BattleScreen.tsx:602`, `battleScreen.css.ts:168`의 CSS width transition이다. faint 박자에서 holdMs도 다시 설정되므로 실제 픽셀 전환 시간은 브라우저로 확인해야 한다. 확정된 사실은 **HP 완료를 기다리는 계약을 입력이 16.67ms로 단축한다**는 것이다.

### 구현 지시

1. 글 읽기 건너뛰기와 HP 이동 완료 대기를 분리한다. damage/heal 진행 중 confirm/cancel/클릭으로 다음 사건이 시작되지 않게 한다.
2. 기존 빠르기 옵션은 보존한다. 단순히 presentation=true만 붙이면 현재 beatFrames가 HP 빠르기 배율까지 제거한다. 예: `skippable`과 `pace policy`를 독립 표현하거나 HP 전용 hold 정책을 둔다. 구체 API는 선택할 수 있으나 입력 차단과 배율 보존은 필수다.
3. 표시 HP와 목표 HP를 구분하고, HP 0 도달 → 기절 몸체 퇴장 → 기절 문구 → 강제교체/다음 사건 순서를 보장한다. HP 0이 된 순간의 엔진 판정과 시각적 퇴장 상태 분리는 현재 구현을 유지한다.
4. 급소/효과 문구, 독·반동, 회복, 연속 공격에서도 앞 HP 이동을 건너뛰지 않도록 한다. 배틀 명령 메뉴와 기술 배우기 질문에는 입력이 중복 전달되지 않아야 한다.

### 완료 조건

실제 buildBeats+BeatRunner를 함께 사용하는 시험으로 30/60/120/144Hz, 지원하는 모든 빠르기, 매 걸음 advance 입력을 검사한다. `faintAt - damageAt >= 실제 HP 이동 시간 - 한 걸음 오차`를 검증한다. 연타와 회복에서도 완료 전에 다음 사건이 접히지 않아야 한다. 브라우저에서는 입력 연타/메시지 클릭 중 HP바 픽셀과 몸체 퇴장을 함께 촬영한다. 이벤트 배열 순서만 검사하는 시험으로 대체하지 않는다.

## 3. 우선 수정 B — 공통 시계 전환이 몸체와 HP에 미완료 (P1, R1 재개)

### 확인한 코드

`src/scene/battle/BattleStage.tsx:412` Slot은 여전히 `useFrame((_, delta) => ...)`의 원시 delta를 아래에 쓴다.

- 424: 등장/퇴장 shown.current, FADE=0.35초.
- 445 / 453: 전진·복귀 lunge, 피격 flinch.
- 528: model.mixer.update(delta).
- 534: 모델 크기 관찰 시간.

반면 기술 VFX·볼·일부 몸체 계산은 battleClock을 쓴다. 공통 시계는 MAX_STEP_MS=100으로 제한되고 visibility hold도 적용된다. 1초 렌더 지연 시 시계는 0.1초만 전진하지만 원시 delta 경로는 1초를 소비할 수 있다. 0.35초 퇴장은 전자가 약 28.6%, 후자는 100%가 된다. 이것은 코드와 시계 진단으로 확인한 불일치이며 실제 지연 영상의 측정값은 아니다.

HP CSS width transition 역시 논리 시계 hold/cap을 알지 못한다. 따라서 재생기만 멈추고 HP 표시는 다른 시간으로 진행할 수 있다. 보고서의 「몸체 등 모든 delta를 제거」 및 R1 완료 표시는 현 코드와 맞지 않는다.

### 구현 지시

1. Slot의 표시 상태·lunge·flinch·AnimationMixer는 battleClock의 소비자별 경과 시간으로 전진시킨다. 읽는 소비자가 tick을 호출하면 안 된다. 단일 소유자가 시계를 전진시키는 현 구조를 유지한다.
2. 마운트/모델 교체/배틀 reset 때 마지막 관측 시간을 초기화하여 음수 경과나 이전 배틀 시간을 소비하지 않게 한다. 같은 프레임 중복 읽기는 중복 진행되지 않아야 한다.
3. HP 보간도 같은 시계의 시작 시각·시작 HP·목표 HP·기간으로 계산하거나, 동등하게 pause/cap을 공유하도록 바꾼다. CSS를 남긴다면 별도 벽시계가 되지 않음을 실제 hold/stall 시험으로 입증한다.
4. 파티클, 볼, 카메라, 기술 완료 콜백, 소리까지 상태 전이 시점을 확인한다. 완전히 끝난 기술의 완료 콜백은 한 번만 호출되어야 한다.
5. 시험은 시계 숫자만 비교하지 말고 몸체/HP 소비 경로를 함께 검사한다. 필요하면 Slot의 시간 적분을 순수 함수로 추출해 시험하고 실제 컴포넌트가 그 함수를 사용하는지 확인한다.

### 완료 조건

200ms/1초 지연, 5초 탭 숨김·복귀, 30/60/120/144Hz에서 HP·몸체·기술·볼의 논리 진행량이 같아야 한다. pause 동안 모두 정지하고 복귀 시 대기 사건을 한꺼번에 소비하지 않는다. A·Z·취소·클릭 연타도 함께 적용한다. 포획 성공/실패와 기절을 실제 화면으로 남긴다.

## 5. 3D 범위 및 시점 전환 승인 조건 (P2)

보고서 §6.2가 이미 인정하는 미완료를 숨기지 않는다. 모든 객체를 무조건 입체로 바꾸라는 뜻도 아니다.

- 건물 외피: building-patch 사용 레시피 0. 주요 문간·모서리·후면을 실제 동선으로 보고 열린 면/깊이 착시가 남은 종류에 검수 레시피를 추가한다. 옛 shell fallback만으로 원 명세 전체 구현 완료라고 표기하지 않는다.
- 실내 벽: 두 사례 수정은 유지. RoomBoundarySegment/openings 및 천장 opt-in 계약은 미구현이다. 정상 문 통과를 막지 않는 구멍 정의와 양면 관찰 조건을 구현하거나 해당 대체 설계·동등한 시각 근거를 명시한다.
- 울타리/낮은 담·간판: 단면/끝점 연결과 앞뒤/지지대 분리 미완료. 실제 시야에서 문제인 표본과 유지 가능한 표본을 구분하고 수정한다.
- 나무: 현재 3변주와 실제 bounds/LOD는 인정. 5-ring 미채택을 자동 결함으로 보지 않는다. 유지 근거는 정면뿐 아니라 아래/옆/수관 안쪽 노출 및 LOD 전환 영상으로 보완한다.
- 풀·꽃·열매, 바닥·절벽, 잔여 actor, 날씨/입자: 검증대기다. 원 명세 조항별 실제 렌더 목록·대표 맵·카메라·판정을 남긴다. unreviewed 282,678을 결함 수로 오해하거나 후보표 0으로 전수 검수 완료를 주장하지 않는다.

## 6. 최종 검증 작업 (P2, 수정 뒤 수행)

1. 배틀 표: 야생 승리/도주, 트레이너 승리/전멸, 포획 성공/실패, 사파리, 더블, 연속 공격, 충전/숨기 기술, 강제교체, 경험치/레벨/기술 습득/진화. 시작~필드 복귀를 정상 입력으로 기록하고 사건 시각과 영상 파일을 묶는다. 단일 정상 턴만으로 전체 모션 완료를 선언하지 않는다.
2. 양 백엔드: 실제 renderer 값을 남긴다. WebGPU 요청 후 WebGL fallback은 WebGPU 통과가 아니다. 기존 story가 WebGPU로 실행된 경로를 활용하고 실행하지 못한 경우 미실행으로 명시한다.
3. R7 다중 줄: 좋은상처약보다 앞선 회복 도구가 있는 가방을 준비한다. 선택 행/도구 ID/수량 전후/HP 전후/턴을 남기고 동일 전투 2~4회 연속 사용도 검사한다.
4. 성능: 동일 맵/좌표/시야/FOV/시각/백엔드/해상도, 자산 준비 완료 기준을 고정해 3회 반복한다. 프레임 시간 중앙값/p95, draw calls, triangles, 메모리 지표와 자산 누락/컴파일 지연을 구분한다.
5. Scale2x: 전체 텍셀 48.1MB 계산은 실제 GPU 메모리나 장면 순회 누수 시험이 아니다. 동일 경로 반복 진입/퇴장 뒤 live textures/geometries와 가능한 메모리 지표의 추세를 측정한다. dispose 호출 존재만으로 「쌓이지 않는다」고 단정하지 않는다.
6. 제품 변경 후 pnpm check를 재실행하고 관련 브라우저 표본을 재검증한다. 최종 코드/build ID와 증거를 연결한다. 배포는 이 검토의 필수 작업이 아니다.

최종 보고에는 「수정 완료 / 의도적 유지(근거) / 검증대기 / 미구현」을 구분한다. A·B 결함을 닫고 해당 영상과 미완료 범위가 정리될 때 전체 승인 여부를 다시 판단한다.
