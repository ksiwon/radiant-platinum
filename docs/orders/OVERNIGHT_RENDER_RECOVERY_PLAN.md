작성: 2026-09-08. 기준: 사용자 검증 요청 ④ 및 현재 작업 트리 코드 검토.

## 2. 작업 순서와 지속 실행 규칙

순서: A 기준선/검사자 보강 → B 배치 신원과 비동기 작업 → C 자원 소유권 → D 전환 체감 → E 콘솔/설치본 → F 최종 검사.

- 자율적으로 수정·짧은 검사·실험을 반복한다. 단계마다 사용자 답을 기다리지 않는다.
- 한 가설은 관측, 반증 실험, 다음 분기를 적고 실행한다. 같은 조건의 긴 여정을 증거 없이 반복하지 않는다.
- 초기 한 가설에 약 45~60분을 써도 새로운 정보가 없으면 미확정으로 남기고 다음 독립 경계를 조사한다. 이 시간은 완료를 포기하는 상한이 아니라 방법을 바꾸는 기준이다.
- GPU 실험은 동시에 여러 개 돌리지 않는다. 다른 검사 프로세스 때문에 부하가 달라졌는지 기록한다.
- 긴 실행은 프로세스 ID·로그·시작 신원을 남기고 진행을 확인한다. 테스트의 전체 상한과 각 단계 상한을 모두 둔다. 개별 evaluate나 자료 읽기가 무한 대기하면 바깥 while 상한도 작동하지 않을 수 있다.
- 실패 실행은 먼저 상태와 컷을 보존한다. 회복 여부를 보려는 후속 조작은 최초 판정을 덮어쓰지 않는다.
- 수정이 필요한 검사 실행 중에는 관련 소스·하네스·데이터를 변경하지 않는다. 종료 또는 명시적 중단 후 수정하고 중단된 결과는 완료로 합산하지 않는다.
- 사용자의 자료·기존 세이브·개인 브라우저 프로필을 보존한다. 진단에는 복사본과 전용 프로필을 사용한다.
- 이 지시만으로 새 커밋·푸시·배포는 하지 않는다. 로컬 수정 및 검증까지 수행한다.

## 3. A — 먼저 검사자의 판정 범위를 고정한다

### A1. waitTerrain의 실제 호출 계약

직접 폴링 방식은 유지할 수 있다. 다만 “모든 waitForFunction async 판정식은 Promise를 참으로 읽는다”를 일반 상식으로 확정하지 않는다. 설치된 Playwright의 해당 구현 또는 최소 브라우저 실험으로 실제 버전의 동작을 확인한다. 최종 반환값이 boolean인지, {ok:false} 객체 자체를 반환했는지도 이전 코드와 대조한다.

프로젝트와 무관한 작은 페이지에서 다음을 검사한다: 계속 false인 비동기 판정, 지연 후 true, throw, 영원히 끝나지 않는 Promise. 현재 waitTerrain 호출부에도 준비 false/true/관측 오류/상한 초과를 직접 주어 관문을 검증한다. 바깥 대기뿐 아니라 개별 관측 실패도 종료 가능해야 한다. 진단 핸들은 사용 후 해제한다.

### A2. 검은 칸 제외 규칙

현재 terrainJudge는 아래 8칸에서 검은 칸을 제외하고 살아 있는 칸 2개 이상·70% 이상을 요구한다. 검은 배경 위 두 칸만 복잡한 이미지면 통과할 수 있다. “검다”는 픽셀만으로 그곳이 원래 화면 밖이라고 증명할 수 없다.

- 고정 대표 장면은 정상 기준 컷과 카메라 조건에 근거한 ROI/허용 여백을 사전에 지정한다. 실패 컷의 검은 영역을 보고 검사 범위를 줄이지 않는다.
- 보편적인 구조 검사와 장면별 의미 검사를 분리한다. 임의 카메라 전체에 동일 바닥 점유율을 강요하지 않는다.
- 기존 정상 6장/실패 6장은 개발 자료다. 같은 12장으로 맞춘 70%를 독립 검증이라 부르지 않는다. 다른 정상 장면·다른 실패 장면으로 검증한다.
- 항상 실행하는 비저작권 합성 대조군: 완전 검정, 하늘 그라데이션, 대부분 검정+두 칸 무늬, 주인공만 있는 형태, 얇은 상단 바닥, 정상 실내 여백 모형, 정상 지형 모형.
- 실제 게임 컷은 로컬 fixture manifest에 경로·해시·기대 장면·기대 판정을 기록한다. 자료가 없으면 해당 절 미실행이며 최종 화면 검증 완료로 합산하지 않는다. 존재하지만 비었거나 해시가 다르면 실패/신원 불일치로 처리한다.
- 이미지 판정이 바뀌면 계약과 roster를 갱신한다. 실패 컷을 성공할 때까지 다시 찍는 루프는 금지한다.

## 4. B — stop-08의 최초 실패 경계를 찾고 수정한다

### B1. 현재 코드에서 우선 조사할 구체적인 경계

`src/scene/ChunkModels.tsx`는 effect 시작 때 `asked.current`를 갱신하고, 비동기 결과를 `placed` 상태로 설정한다. 커밋 후에는 `placed`의 신원이 아니라 현재 `asked.current`로 `markTerrain`을 호출한다. 재질도 `pending.current`와 `placed`를 따로 전달한다. 이는 서로 다른 작업의 메타데이터·자원·배치가 결합될 수 있는 구조다. 실제 발생은 지연 순서 실험으로 확인한다.

effect 의존성은 grid/chunkIndex/radius/texSet/groundAt이며, asked의 mapId/matrix는 mutable world에서 읽는다. 같은 행렬·청크 안에서 존만 바뀌면 맵 이름이 달라져도 같은 지형을 재사용할 수 있다. 맵 ID 동등성만 요구해 정상 재사용을 실패로 보지 않는지도 확인한다. 반대로 6/116과 3/0처럼 행렬이 다른 경우는 이 예외로 덮지 않는다.

`src/scene/chunkMesh.ts`의 청크·텍스처 캐시는 Promise를 보관한다. 일부 reject는 캐시를 지우지만 pending은 남을 수 있고, 공통 `format` Promise의 실패 수명도 따로 확인해야 한다. 이 구조만으로 이번 미완료 원인을 단정하지 않는다.

### B2. 하나의 작업을 끝까지 연결하는 기록

terrain generation/request ID를 발급하고 다음 신원을 처음에 고정한다:
grid identity, matrix, map/zone, chunk center, radius, texture set, asset provider/data identity.

단계별 기록: requested → cache hit/miss → bytes begin/end → decode begin/end → geometry build begin/end → state submitted → scene committed → rendered → superseded/failed/released.

각 하위 작업에는 resource key, 시작/완료 시각, 캐시 Promise 신원, 세대, 결과를 남긴다. 화면에는 최신 요약만, 상세는 크기가 제한된 링 버퍼를 사용한다. 매 프레임 전체 씬/객체를 직렬화하거나 모든 객체를 강한 참조로 붙잡지 않는다.

원인 분기:

| 관측 | 다음 조사 |
| --- | --- |
| 새 요청 자체가 없음 | effect 의존성, 상태 업데이트, 컴포넌트 생존, 존/행렬 전환 |
| bytes 완료 없음 | provider/요청 큐/취소/공유 Promise/자료 읽기 |
| bytes 완료, decode/build 미완료 | 동기 CPU 작업, 파서, 예외, 메인 스레드 지연 |
| 결과 생성, state 제출 없음 | alive/세대 검사, stale 결과 처리 |
| state 제출, 커밋 없음 | 리마운트, 예외, 다른 업데이트와 병합, React 트리 |
| 커밋 완료, 표식만 옛것 | 표식 소유권과 batch 연결 |
| 올바른 표식, 실제 지형은 옛것 | mesh/batch UUID, React key, 공유 자원 재사용·해제 |

“load가 끝내 안 끝났다”는 위 begin/end 중 특정 미완료 작업을 찾은 뒤에만 확정한다. fps 4에서는 메인 스레드 처리 지연과 Promise 영구 정체를 구분한다.

### B3. 수정 계약

가능한 최소 구조로 배치 데이터·배치 신원·소유 자원을 하나의 불변 batch로 묶는다. 실제로 커밋된 batch의 신원만 준비 표식에 게시한다. 단순히 asked를 최신 맵으로 다시 쓰는 것은 고침이 아니다.

- 새 세대가 시작되면 옛 응답은 새 씬을 덮지 못한다.
- 취소·오류·타이틀 이동·언마운트·빌드 도중 throw에도 해당 작업이 만든 미게시 자원을 정리한다.
- 같은 자원을 여럿이 기다릴 때 한 소비자의 취소가 다른 소비자의 공유 요청을 파괴하지 않는다.
- 실패한 오래된 Promise의 cleanup이 같은 key에 생긴 새 Promise를 지우지 않도록 identity를 비교한다.
- pending/failed 상태를 관측 가능하게 하고 영원한 조용한 대기를 없앤다. 실제 지연 측정에 근거한 제한된 재시도와 재시도/타이틀 복귀 UI를 둔다.
- Promise.race timeout은 원래 작업을 취소하지 않는다. 늦은 성공이 돌아와도 게시를 막고 소유 자원을 정리해야 한다.
- 자동 무한 재시도, 매 프레임 재요청, 전체 캐시 주기 삭제를 넣지 않는다.

회귀 실험은 지연을 제어한 A→B→A, 완료 순서 역전, 한 요청 reject, 한 요청 미완료, 중간 언마운트, 배치 구성 도중 throw, 공유 요청 두 소비자, 같은 행렬 내 존 변경을 포함한다. 실제 코드의 호출 경계에 주입하여 결과와 자원 정리를 검증한다.

## 5. C — 기하와 텍스처의 소유권을 함께 닫는다

누적 생성 수와 현재 GPU 등록 수, 씬 도달 가능 수를 명확히 구분한다. renderer 통계의 실제 버전/백엔드 필드를 읽고 의미를 확인한다. 누적 생성 수가 증가하는 것은 그 자체로 누수가 아니다.

기하 UUID별로 생성 위치·배치/캐시 소유자·씬 부착/분리·dispose·재사용을 추적한다. 최초 생성 스택은 샘플링하고 추적 자체가 객체를 붙잡지 않게 한다. 반복 왕복 전에 캐시 예열을 하고 같은 자료 집합만 왕복한다.

특히 조사할 것:

- `useMemo`/render 중 새 geometry 생성 후 React가 그 결과를 폐기하는 경로.
- 합성에 사용한 중간 clone/split/merge 결과 중 최종 mesh에 붙지 않는 것.
- `primitive` 및 `dispose={null}` 아래 자원의 실제 소유권.
- StrictMode의 setup/cleanup 반복과 실제 unmount의 차이.
- ChunkModels의 pending/standing 참조 교체, state 커밋이 생략된 배치, 구성 중 throw.
- 공유 cache geometry를 배치가 해제해서 재업로드가 반복되는 경우.

`ownsMap`은 방향이 맞다. 하지만 material 복제 시 userData만 복사되고 map은 공유될 수 있으므로 clone/재사용 경로를 확인한다. 소유권 표식이 두 소유자를 만드는지 검증한다. 공유 자원은 마지막 사용자가 떠날 때만 해제하고 배치 전용 자원은 정확히 정리한다. 빈 catch나 일괄 dispose로 증상을 덮지 않는다.

완료 기준: 예열 후 같은 왕복을 최소 20회 수행하고 동일 시점의 live geometry/texture 수가 설명 가능한 범위에서 안정되어야 한다. 5회 단위 값과 마지막 값, 생성-해제 잔액을 남긴다. 수가 오르면 원인별 미해결 자원 수를 남기며 “텍스처 전체 해결”이라 쓰지 않는다. 공유 자원을 다시 쓰는 장면의 시각 회귀도 확인한다.

## 6. D — 카메라 관문 통과와 사용자 경험을 분리한다

현재 drift는 camera position과 goal의 거리만 잰다. target/look 및 fov도 보간되므로 위치가 같아도 화면은 바뀔 수 있다. NaN은 `drift > threshold`를 통과할 수 있다. 숫자 유한성, 실제 렌더 카메라의 행렬, 타깃/FOV 안정 여부를 필요한 범위에서 확인한다.

2.4~8.5초 기다려 검사가 통과한 것은 관문의 효과다. 그 시간 동안 사용자가 미완성 방을 보는 문제까지 해결한 것은 아니다.

새 전환에서 페이드 시작, 지형 커밋, 카메라 초기화/안정, 페이드 해제, 입력 해제 시각을 함께 잰다. 워프처럼 불연속 이동이면 목적지의 유효 지형·room bounds가 생긴 뒤 카메라를 전환 시점에 한 번 초기화할 수 있는지 검토한다. 일반 보행 보간과 스크립트 카메라·HM 컷인은 보존한다. 임의 sleep으로 화면을 오래 가리지 않는다.

맵 전환 공개 전에 필요한 준비가 안 됐으면 기존 복원/오류 UI와 조화되는 loading 상태를 사용한다. 영구 검은 화면이나 보이지 않는 맵에서 조작만 되는 상태를 허용하지 않는다. timeout 후 저장을 지키며 재시도/타이틀로 빠져나올 수 있어야 한다.

정상 왕복, 연속 워프, 계단, 스크립트 소유 페이드, HM 컷인, 저장 복원, 1인칭/3인칭 지원 범위를 검사한다. 냉/온 캐시별 대기 시간과 화면 노출을 보고하며 새 성능 SLO를 기존 계약인 것처럼 꾸미지 않는다.

## 7. E — 간헐적 콘솔 오류와 설치된 프로덕션

R3F 내부 reconciler 경로라는 관측은 유지하되 컴포넌트와 실제 실패 detail은 미확정이다. 소스맵/예외 중단 또는 제한된 진단 래퍼로 첫 실패만 잡는다. 원래 performance.measure의 this·인자·반환·예외를 보존한다. 거대한 props를 직렬화하거나 복제를 매 프레임 반복하지 않는다.

실패 전후 컴포넌트명, prop key, 타입, detail 구성 단계, 스택을 기록한다. 원래 오류를 다시 던지고 콘솔을 숨기지 않는다. 새 문자열 오류 “out of memory”만으로 실제 메모리 고갈이라 판단하지 않는다.

기하 진단과 긴 전환 실험에 제한된 수집기를 함께 붙일 수 있지만 계측 부하를 기록하고 계측 없는 대조도 둔다. 446회 무오류를 수정 성공으로 부르지 않는다. 최소 재현 후 애플리케이션 변경/검증된 의존성 수정 중 가장 작은 해결을 선택한다. 번들 직접 편집만 남겨 재설치하면 사라지는 수정은 금지한다.

프로덕션은 최종 build와 실제 설치 자료로 전용 프로필/같은 origin에서 잰다. 개발 /data 주입으로 대신하지 않는다. 기존 설치 프로필을 재사용하면 데이터 신원·설치 상태를 확인하고 fresh 설치와 구분한다. ROM/덤프를 재설치해야 하면 절차와 소요 시간을 기록한다. 로딩 오류를 먼저 해결해야 긴 경로가 의미 있으면 설치 검증만 준비한 뒤 계속한다.

배포본이 조용해도 개발 오류는 별도 결과로 남긴다. 개발·profiling·일반 production 빌드와 DevTools 여부를 구분한다.

## 8. F — 최종 검사와 증거

수정이 끝난 소스에서 check/build를 수행한다. 보고된 98ec47e build를 현재 결과로 재사용하지 않는다. 테스트와 빌드가 서로 다른 소스를 읽지 않도록 final candidate를 고정하고 실행 시작/종료의 신원을 확인한다.

필수 실행:

1. 해당 수정 전 실패/후 성공의 짧은 재현과 자원 반복 검사.
2. render:first WebGPU/WebGL, gpu:loss. 실제 지원 인자·roster로 수행하고 미실행 환경을 합산하지 않음.
3. 건너뛰기 없는 새 게임 journey: 첫 배지, 저장·이어하기, 대표 지형 컷, 콘솔.
4. e2e 전체와 story 88자리의 현재 roster. 이전 숫자를 기대치로 하드코딩하지 않음.
5. 설치된 프로덕션의 대표 전환/긴 경로와 오류 대조.

하나의 지형 준비 실패로 뒤의 길목을 검사하지 못하면 원인 항목은 FAIL, 실행 불가능한 종속 항목은 BLOCKED/미실행으로 명시한다. 실제 실행해서 실패한 항목을 임의로 BLOCKED로 바꾸지 않는다. 계약을 바꿀 때만 새 판정으로 재실행하고 원시 JSON은 편집하지 않는다.

최종 봉투는 source/harness/data/artifact/contract/환경/expected-executed와 시작·끝 신원을 확인한다. 로컬 컷 fixture가 없으면 단위 검사 skip을 전체 시각 합격으로 바꾸지 않는다. 정상 첫 배지 구간 재개는 진단이며 전체 journey를 대체하지 않는다.

긴 검사에서 새 실패가 나오면 해당 구간의 최초 경계를 보존하고 좁혀 고친다. 최종 코드 변화에 영향을 받는 증거만 정확히 다시 만들고, 다이제스트 규칙이 무효로 만든 결과는 재실행 없이 살리지 않는다.

## 10. 외부 근거와 적용 범위

- [Three.js 자원 해제](https://threejs.org/manual/en/how-to-dispose-of-objects.html): material 해제는 texture 해제가 아니며 공유 자원의 수명을 따로 관리해야 한다. 이 프로젝트 특정 누수 원인까지 입증하는 자료는 아니다.
- [Three.js cleanup](https://threejs.org/manual/en/cleanup.html): geometry/material/texture의 명시적 해제 원칙. 전역 일괄 해제 지시로 해석하지 않는다.
- [Playwright waitForFunction](https://playwright.dev/docs/api/class-page#page-wait-for-function): truthy 결과를 기다리는 API 계약과 timeout/polling. 특정 설치 버전의 async 평가 세부는 최소 재현/구현으로 확인한다.
- [React Performance tracks](https://react.dev/reference/dev-tools/react-performance-tracks): 개발 및 profiling 기능 범위. 설치된 프로젝트 production의 무오류를 대신 증명하지 않는다.
- [React useEffect](https://react.dev/reference/react/useEffect): 의존성 변화와 cleanup 수명. 공유 캐시 소유권은 애플리케이션에서 별도 설계한다.

이 문서 작성 과정에서는 코드와 공식 문서를 검토했으며 제품 변경·게임 테스트 재실행·컷 육안 검증은 하지 않았다. 보고의 실행 수치는 사용자 제공 결과다.
