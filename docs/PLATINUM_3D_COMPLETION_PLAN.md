### 1.1 ‘완전한 3D 플래티넘’의 정의

완성은 다음 조건의 교집합이다.

- **실행:** 지원 PC에서 설치·시작·재접속·오류 복구가 된다.
- **공간:** 카메라가 움직여도 주요 사물과 길이 입체적으로 성립한다.
- **인물:** 주요 인물을 대사 이름 없이도 외형으로 구분할 수 있다.
- **행동:** 조작·모션·소품·충돌·이벤트 결과가 같은 행동을 표현한다.
- **모험:** 정상 입력으로 처음부터 엔딩·후일담으로 연결된다.
- **전투:** 규칙·표시·연출·보상이 일치한다.
- **보존:** 리포트 이후 상태가 설치 갱신·재접속에서도 유지된다.
- **품질:** 성능·접근성·로케일·시각 품질 기준을 통과한다.
- **범위 정직성:** 구현하지 않은 원작 기능을 숨기거나 완전 재현이라고 부르지 않는다.

DOM 메뉴·텍스트, 지도·아이콘, 입자·나뭇잎의 alpha plane은 정상적인 표현 기법이다. 화면의 모든 면을 입체로 부풀리는 것을 목표로 하지 않는다.

## 3. 새로 확인한 보강 지점

아래는 이번 정적 분석과 읽기 전용 합성 검사 결과다. 실제 게임에서 재현하지 않은 것은 위험 가설로 표시한다.

### 3.1 증거의 소스 지문에 신규 파일이 빠진다 — 직접 확인

evidence.mjs의 sourceFiles()는 git ls-files로 추적 파일만 읽는다. 현재 신규 구현은 아직 미추적 상태다.

이번 함수 호출 결과:

| 파일 | sourceFiles 포함 |
|---|---|
| src/scene/Stage.tsx | true |
| src/state/rendererStore.ts | **false** |
| src/ui/screens/RendererTrouble.tsx | **false** |

따라서 해당 신규 파일의 내용만 바꾸면 소스 지문에 반영되지 않을 수 있다. 출시 직전 전부 추적한다는 운영 규칙만으로 개발 중 증거의 정확성이 확보되지는 않는다.

**작업:** 앱 입력 목록은 추적 파일과 ignore되지 않은 신규 앱 파일을 포함한다. raw/public 추출 산출물은 섞이지 않게 기존 제외 계약을 적용한다. 또는 미추적 앱 입력이 있으면 증거 생성·판정을 명시적으로 막는다. 두 정책 중 하나를 일관되게 선택한다. 테스트를 위해 자동 git add하지 않는다.

### 3.2 필수 검사 목록을 결과 봉투가 스스로 정한다 — 직접 확인

validateEvidence에 story의 expectedCases·executedCases·results를 모두 임의의 one 한 건으로 맞춘 합성 봉투를 주면 현재 **ok: true**다. 파일은 수정하지 않았고 합성 입력으로 검증 함수만 호출했다.

이 검사는 배열 사이의 일치는 확인하지만, **원래 반드시 실행해야 할 story case 집합**과 독립적으로 대조하지 않는다. 실제 하네스가 현재 올바른 목록을 넣는 것과 판정기가 축소된 목록을 거부하는 것은 다른 보장이다.

**작업:** suite별 정본 case ID·검사 계약 버전을 판정기가 소유한다. expected/executed/results의 ID가 정본과 정확히 일치해야 한다. ID 타입·중복·결과 중복·selection·필수 모드 누락을 검증한다. 데이터에 따라 달라지는 목록은 해당 데이터 지문까지 묶는다.

### 3.3 GPU 복구 검사의 보장 범위가 좁다 — 직접 확인

- 현재 gpuLoss.json은 backendBefore와 rows만 저장한다. 새 evidence 봉투·GPU 이름·버전이 없다.
- gpuLoss.mjs는 FAIL이 있을 때만 종료 1을 낸다. BLOCKED뿐이면 종료 0이 가능하므로 종료 코드만으로 합격 처리하면 안 된다.
- 루프 중복 검사 stepsIn은 실제 손실 전 걸음 baseline을 측정하지 않고 상수 4와 moved <= 8을 비교한다. 이동 0도 이 항목 자체는 통과한다. 앞선 이동 검사가 있더라도 ‘같은 조건에서 두 배가 되지 않음’을 강하게 증명하지는 못한다.
- 이번 기록은 WebGL2 필드 복구다. WebGPU 손실·배틀 중·스크립트 중·설치본 장시간 복구는 별도다.

**작업:** 장치 손실 suite를 봉투 계약에 추가하고, 필수 BLOCKED는 출시 실패 또는 별도 미검증으로 처리한다. 장애 전후 동일한 장애물 없는 구간에서 위치 이동량·시뮬레이션 tick·리스너/시스템 수를 비교한다.

### 3.4 정지 사유가 여러 곳에서 같은 boolean에 쓰인다 — 정적 위험

rendererStore.freeze()는 gameLoop.paused=true로 만들지만 EngineDriver의 visibilitychange는 document.hidden만 대입한다. 복구 중 탭으로 돌아오면 정지 사유가 덮일 수 있다. 또한 markReady는 renderer.init 완료 시점이며 전체 씬 재구성과 안전한 입력 재개의 완료 시점은 아니다.

**작업:** renderer, document-hidden, fatal-scene 등의 정지 사유를 한곳에서 합성한다. 배틀의 상태별 진행 정책은 별도로 유지한다. 복구가 필요한 자산·씬·스크립트 준비를 확인한 뒤 입력을 풀어야 한다.

### 3.5 마지막 오류 경계·세대 경합 — 정적 위험

- 최종 기본 state.gl.render 호출의 예외는 현재 명시적 보호가 없다.
- React 씬 렌더의 동기 오류 경계는 보고에서도 미완이다.
- Stage의 과거 renderer.init 결과와 onDeviceLost 콜백을 현재 generation과 대조하는 명시적 차단이 보이지 않는다.
- 후처리 생성 도중 일부 자원을 만든 다음 실패했을 때의 정리도 추가 검수 대상이다.
- 재시도가 끝나지 않으면 recovering 화면에 사용 가능한 탈출 동작이 없어질 수 있다.

**작업:** 동기 씬 오류, 프레임 콜백 오류, 비동기 초기화 실패를 각각 맞는 경계에서 처리한다. 이전 세대의 완료/손실은 현재 상태를 바꾸지 못하게 한다. 복구 시간 초과·취소·마지막 리포트 복귀를 제공한다.

React 오류 경계는 모든 비동기·이벤트 오류를 포괄하지 않으므로 하나의 경계로 전부 해결했다고 보고하지 않는다. [React 오류 경계](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary)

## 4. 제품 범위와 최종 도착점

### 4.1 두 개의 완성 단계

| 단계 | 포함 | 완료 명칭 |
|---|---|---|
| C1: 3D 모험 완성판 | 현행 PC 싱글플레이, 메인 스토리·후일담 접근, 완성된 필드/배틀 표현, 저장·복구·성능 | 지원 범위의 완성된 3D 리메이크 |
| C2: 오프라인 플래티넘 확장 완성판 | 나머지 프런티어·콘테스트·지하통로 싱글플레이 및 수집 대체 정책 | 오프라인 범위 확장 완성 |
| 별도 제품 | 실시간 통신 대전·교환·GTS, 모바일, VR | 별도 기획 필요 |

이번 새 기획에는 C2의 제작 요구사항까지 포함한다. 다만 기존 범위 밖 기능이므로 구현 담당자가 C1 도중 자동으로 착수하지 않게 한다. 원작의 통신 기능까지 없는 상태를 ‘원작 전 기능 완전 재현’이라고 표현하지 않는다.

### 4.2 유지할 제품 결정

- 원작 플래티넘의 진행·규칙과 검증된 기존 오프라인 예외를 보존.
- 등신 캐릭터 중심의 3D 시각 방향 유지.
- 3인칭 기본, 1인칭 보조 시점.
- 현행 공용 ui/theme 기반의 밝고 읽기 쉬운 UI 유지.
- 수동 리포트, 사용자 로컬 자료 변환, OPFS 자산 사용 유지.
- 오류 때문에 원본·설치본·정상 세이브를 일괄 삭제하지 않음.
- 배포용 자산 경계와 명시적 사용자 제보만 전송하는 정책 유지.

## 6. PT-01 / PT-02 — 짧게 마무리할 선행 단계

### 6.1 검증 계약의 완료 조건

- 신규 앱 파일 추가·수정·삭제가 sourceDigest에 반영되거나 생성이 명시적으로 거절된다.
- docs만 수정하면 게임 sourceDigest는 유지된다.
- 추출된 게임 데이터가 실수로 공개 소스 목록·배포물에 포함되지 않는다.
- 정본 필수 case를 한 건으로 축소한 봉투가 실패한다.
- 중복 ID, 누락 ID, 알 수 없는 status, 잘못된 타입, 부분 실행이 실패한다.
- story는 실제 개발 소스, 설치 E2E는 실제 dist에 묶인다.
- 검사 논리 변경은 별도 harnessDigest 또는 suiteContractVersion으로 기록한다. 도구 변경을 무조건 무시하지 않는다.
- buildStamp의 소스 지문과 artifact 지문을 연결해 무엇으로 만든 dist인지 추적한다.
- 실행 시작·종료 시점의 대상 지문이 달라지면 무효 처리한다.
- gpu:loss도 환경·backend·버전·결과·대상 지문을 갖는다.
- dirty 후보를 몰래 clean으로 표기하거나 기존 결과를 손으로 PASS로 바꾸지 않는다.

### 6.2 복구 상태의 완료 조건

렌더러의 ready와 게임의 play-ready를 구분한다. 로더와 씬 재구성 완료를 기다리되, 끝나지 않으면 제한 시간 후 복구 실패 화면으로 전환한다.

| 장애가 난 시점 | 기대 결과 |
|---|---|
| 타이틀/인트로 초기화 | DOM 오류 안내·재시도 |
| 필드 이동 | 정상 위치·이벤트 상태로 재개, 눌린 키 초기화 |
| 워프 중 | 이전/다음 맵 중 유효한 한 상태로 확정 |
| 배틀 명령 선택 | 선택·PP·턴이 중복 진행되지 않음 |
| 배틀 연출 중 | 같은 결과 한 번만 반영, 연출 재생 정책 명시 |
| 진화/부화/포획 | 개체·도감·보상 중복 생성 없음 |
| 저장 중 | 기존 또는 새 정상 리포트 중 하나 보존 |
| 복구 중 탭 전환 | 정지 사유가 풀리지 않음 |
| 연속 손실 | 자동 복구 횟수 상한 유지·수동 선택 |
| 과거 renderer의 늦은 응답 | 현재 세대를 ready/lost로 바꾸지 않음 |

복구할 수 없는 임시 상태는 마지막 리포트로 돌아가게 한다. 비정상 순간의 강제 자동 저장으로 해결하지 않는다. 오류 UI에는 실제 원인을 단정하지 말고 가능한 원인·현재 관찰 정보·다음 행동을 분리한다.

Three.js의 onDeviceLost 계약을 현재 설치 버전에서 확인하고 공용 어댑터에 한정한다. [Three.js Renderer](https://threejs.org/docs/pages/Renderer.html)

## 9. PT-05 — 캐릭터, 모션, 필드 행동

### 9.1 고유 인물 완성

사람 모델 1,895/1,895 기록은 ‘3D 존재’ 수치다. 마박사 gentleman 대역, 핸섬·플루토 재색칠 같은 고유 외형 문제는 별도다.

2. 주인공 남/여, 라이벌, 관장·사천왕·챔피언.
3. 반복 노출 주민·점원·간호사.
4. 희귀 NPC와 작은 장식 차이.

고유 모델이 필요한 경우 기존 BDSP 메시를 무관한 캐릭터로 이름만 바꾸지 않는다. 지원 입력에서 얻을 수 있는 부품으로 적절하게 구성하거나 프로젝트가 사용할 수 있는 별도 자산을 제작한다. 신규 자산의 출처·배포 위치·생성 파이프라인은 기존 경계 규칙에 맞춘다.

**검수:** 원근 왜곡이 작은 앞/옆/뒤 컷, 주인공 옆 비율, 걷기·회전·손 동작 영상, 조명별 얼굴·옷 색. 발바닥 기준 원점·정면 +Z·skin 적용 bounds를 일관되게 사용한다.

### 9.2 필드 행동 상태

각 행동은 아래 계약을 가진다.

```text
가능 조건 → 입력 소유권 확보 → 준비 → 실행 → 판정/이동
→ 종료 → 소품/포즈 정리 → 입력 반환
```

취소·맵 전환·GPU 손실·실패도 같은 정리 경로를 통과한다.

| 행동 | 필요한 완성 |
|---|---|
| 걷기·달리기 | 실제 속도에 맞는 보폭·발 미끄러짐 최소화 |
| 자전거 | 가속과 3/4단 모드 구분, 모드 전환·램프·비탈·정지 자세 |
| 낚시 | 낚싯대·줄·던지기·물결·입질·실패·회수 |
| 물주기 | 손 소품·물 효과·옆 밭 이동·종료 |
| 파도타기 | 승선·수면 높이·탈것·해안 하차 |
| 폭포·록클라임 | 이동 시간·포즈·접지·시작/종료 위치 |
| 공중날기 | 포켓몬·탑승·이륙·도착·날개 박자 |
| 문·승강기·배 | 모델 움직임·음향·워프 결과가 같은 사건 |

원작의 모션이 없다고 입력 효과만 만들고 완료하지 않는다. 절차형 보완은 허용하되 원작 클립과 같은 뼈를 동시에 덮어쓰지 않게 제어권을 관리한다.

### 9.3 설치본 외형

monVariants 변환은 이미 존재한다. 새로 만들 작업은 아니다.

- 기본/추가 외형 설치의 실제 상태를 화면에 표시.
- 종·폼·성별·이로치의 선택 키가 전투·필드·진화·미리보기에서 일치.
- 외형팩 미설치 시 잘못된 외형을 조용히 ‘정상 외형’이라고 부르지 않음.
- C1 완전 외형 검수는 해당 옵션이 설치된 프로필에서 수행.
- 무성 포켓몬·여성 외형·동적 폼도 매트릭스에 포함.
- 변환 수정 시 개발 추출기와 브라우저 변환기를 같이 고치고 포맷을 필요한 그룹만 갱신.

## 10. PT-06 — 배틀의 규칙·연출·정보 완성

기존 PARITY §2.24의 other 목록을 다시 수집한다. 준비기·방어·충전·타격 횟수·대상 없음·능력치 변경·팀 회복을 우선한다.

- 큰 포켓몬·작은 포켓몬·부유·더블 배틀 네 자리를 모두 시험.

| 시설전 | 일반 모험 경험치·돈·기록 규칙이 침범하지 않음 |

## 11. PT-07 — 처음부터 엔딩까지 정상 연결

### 11.1 Journey 검증

기존 story는 장면을 여는 데 계속 사용한다. Journey는 다음 관문에 필요한 상태를 **이전 관문 정상 플레이의 결과**에서 가져온다.

- 새 게임→스타팅→첫 라이벌→첫 체육관.
- 2~8번째 배지의 지역·장치·필수 이벤트.
- 갤럭시단·호수·본부·창기둥·깨어진 세계.
- 챔피언로드→사천왕→난천→명예의 전당.
- 크레딧→리포트→이어하기.
- 배 이동→배틀존·강철섬·스타크산 등 후일담 접근.

각 edge는 시작/종료 세이브 지문, 앱/콘텐츠 지문, 로케일, 입력, 획득 도구·배지·플래그, 종료 위치를 기록한다. 전체 여정을 한 번에 자동 주행하기 어렵다면 구간별로 끊되 세이브 체인은 실제로 이어져야 한다.

체크포인트 주입은 그래픽 시험용이다. 진행 그래프를 통과한 것으로 세지 않는다.

### 11.2 종료하지 않는 스크립트 방지

VM의 명령 구현률보다 지원 범위에서 도달 가능한 미해결 명령 수를 본다.

- 결과 변수를 안 쓰는 서비스·미지원 메뉴가 우연히 성공하지 않음.
- 대사·애니메이션·소리 대기가 종료 또는 취소로 풀림.
- 시야 트리거·타일 트리거·워프 실행 순서 보존.
- 잠금 해제가 빠지면 지도/명령/PC/대기 상태를 로컬 기록.
- 해결을 위해 스크립트를 무조건 건너뛰는 timeout을 넣지 않음.

### 11.3 필수 엔딩 연출

명예의 전당과 크레딧은 출시의 마지막 인상이다.

- 실제 파티 6마리와 주인공의 위치·키·폼·성별·이로치 일치.
- 전당 기록·엔딩 플래그·세이브 시점이 연출과 일치.
- 크레딧 글과 배경 3D 장면 전환을 완성. 기존 기록의 7장면은 작업 대장에 올린다.
- GPU 복구·연출 스킵 후 전당 기록이 중복되지 않음.
- 정상 종료 후 이어하기가 후일담 상태로 진입.

아래는 **새 목표치**다. 현재 달성 수치로 제시하지 않는다.

GPU·OS·드라이버·브라우저·전원 모드·backend·DPR·실제 화면 크기를 기록한다. 현재 960×640 WebGPU A/B와 WebGL 손실 결과만으로 1080p 성능 합격을 선언하지 않는다.

### 12.2 최적화 순서

1. I/O·디코드·객체 생성·GPU 업로드·셰이더·첫 표시·입력 해제 span.
2. cold/warm, WebGPU/WebGL2, 정상/복구 후를 분리.
3. 중복 material·skeleton·불필요 활성 mixer 축소.
4. 필요한 맵만 사전 로딩·작업 분할·취소 가능한 요청.
5. 실측 후 캐시 바이트 예산과 LRU.
6. 마지막에 texture 압축·mesh 압축의 총비용 비교.

KTX2 등의 디코더 요구사항·CSP·설치 시간·추출기 동등성을 확인한다. Three.js 버전 업그레이드를 해결책으로 가정하지 않고 현행 버전의 재현 증거부터 확보한다.

### 12.3 품질 프리셋

Low/Standard/High가 render scale·그림자·블룸·장식 입자·장식 시야를 제어한다. 충돌·NPC·필수 아이템·발판·조우는 동일하다. 사용자 고정 선택을 우선하고 자동 조절에는 관측 시간·상하향 차이·최소 유지 시간을 둔다.

### 12.4 자원 소유권

CPU 디코드, GPU geometry/texture, animation, Blob URL을 따로 센다. shared geometry와 splitShadow의 공유 버퍼를 개별 소비자가 제거하지 않는다. 원본 자산·활성 참조·퇴출 후보를 구분한다.

정확한 GPU 메모리를 모든 브라우저에서 얻는다고 약속하지 않는다. 앱 소유 바이트·URL·객체 수와 사용 가능한 heap 수치를 기록한다. warm 후 메모리 증가가 의도된 bounded cache인지 반복 누수인지 구분한다.

## 13. PT-09 — 설치·저장·업데이트 안정성

### 13.1 설치

지원 ROM·BDSP 폴더 확인 → 용량·선택 외형 안내 → 변환 → 검증 → 준비 완료.

- 파일 수·완료 그룹·진행 단계를 구분. 모르는 남은 시간을 확정값으로 표시하지 않음.
- 취소·Worker 종료·탭 닫기·quota 초과 후 그룹별 재개.
- 바이트 hash와 format을 모두 확인.
- 선택 외형을 나중에 추가해도 리포트 보존.
- locale별 개발/브라우저 출력의 geometry·변환·재질·클립·픽셀 대조.
- 업데이트는 필요한 그룹만 staging 후 검증·승격.
- 예전 정상 설치를 먼저 전부 지워야 하는 흐름 금지.

### 13.2 저장

현행 TMP→재읽기 검증→현재 슬롯 승격을 유지하고 보강한다.

- 요청 직렬화와 일관된 snapshot.
- TMP 읽기 실패도 구조화된 실패 결과.
- 다중 탭은 단일 작성자, 읽기 탭의 상태가 오래됐으면 쓰기 전에 검증.
- 다른 탭의 삭제·재설치·불러오기도 같은 소유권 계약.
- 모든 지원 SAVE_VERSION·다른 locale·손상/미래 버전·TypedArray 경계 검사.
- 불러오기 실패가 기존 리포트를 덮지 않음.
- 이전 정상 리포트 복구와 파일 내보내기 제공.

Web Locks는 같은 origin의 탭/Worker 사이 작업 조정에 사용할 수 있다. API가 없을 때의 보수적 동작도 설계한다. [MDN Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)

### 13.3 앱 갱신·오프라인

플레이 중 강제 새로고침하지 않는다. 새 버전 안내→리포트→재시작 흐름을 제공한다. 코드/SW/콘텐츠 포맷이 섞이는 상황을 시험한다. 지연 로딩 배틀 청크가 아직 준비되지 않은 채 오프라인으로 바뀌는 사례도 포함한다.

## 15. PT-12 — 오프라인 콘텐츠 확장 설계

C1 완료 뒤 착수할 제품 범위 제안이다. 이 절을 읽었다는 이유만으로 원작 데이터를 임의로 바꾸지 않는다.

### 15.1 프런티어 네 시설

팩토리 기존 구현을 공통 베이스로 삼되 시설 고유 규칙을 섞지 않는다.

| 시설 | 구현 요구 |
|---|---|
| 타워 | 파티 제약·연전·상대 편성·시설장·BP·연승 기록 |
| 스테이지/홀 | 종 선택·타입 도전·연속 기록·제약 |
| 캐슬 | 자원/포인트·회복·정보·상대 조건 선택 |

각 시설에 접수→선발→전투→보상→중단/재개→기록 화면을 갖춘다. 형식적인 메뉴만 먼저 열어 플레이어를 갇히게 하지 않는다. 정확한 값·이름·규칙은 기존 원작 근거에서 확인한다.

### 15.2 콘테스트

컨디션·참가 등급·평가·라운드·NPC AI·기술 효과·리본·관련 도구·요약 화면까지 한 흐름으로 만든다. 터치/두 화면 동작은 키보드·마우스에 맞게 재설계하고 판정 근거를 명시한다. 승패와 리본이 저장·재로드 후 유지되어야 한다.

### 15.3 지하통로

별도 공간 진입/복귀, 이동, 채굴 상호작용, 채굴 보상, 소지품·장식·비밀기지, 저장을 하나의 패키지로 설계한다. 원작 통신 의존 행동은 NPC 대체/제외 등 정책을 먼저 정한다. 로컬 구현에 멀티플레이 서버를 암묵적으로 포함하지 않는다.

### 15.4 493종 획득 그래프

종별로 야생·선물·번식·진화·이벤트·교환 의존을 그래프로 관리한다. 자료가 있는 것과 플레이어가 획득 가능한 것을 구분한다.

추천은 **원작 기반 모드와 오프라인 완성 모드**를 구분하는 것이다. 대체 경로는 진행 단계·비용·반복 가능·희소성·세이브 호환을 명시하고 검증한다. 화강돌 무덤·통신 전용 종·조각 입수처럼 막힌 경험을 우선 해결한다. 기존 시원 선물은 별도 추가 콘텐츠임을 유지한다.

원작 전량 재현으로 주장할 수 없는 제한은 제품 설명에 그대로 남긴다.

### 16.1 검사 운용

- 변경 후 관련 테스트를 먼저 실행하고 통과하면 pnpm check.
- 빌드 대상 코드가 바뀌었으면 해당 후보에서 build와 필요한 E2E.
- story 장면 검사·story --fight·story --chain은 목적을 나눠 실행.
- production 확인은 saves:check처럼 실제 세이브 UI를 사용.
- Journey와 GPU 복구 확장 suite는 새 계약에 맞춰 추가.
- 지원하지 않는 GPU/브라우저를 software 결과로 채워 PASS 처리하지 않음.
- 기존 전체 결과를 부분 재실행 결과로 덮기 전에 식별 가능한 이력을 보존.
- 긴 검사 중 소스/배포물이 바뀌면 결과를 무효 처리.

### 16.2 배포

깨끗한 후보 소스와 lockfile → build → 경계/출처 검사 → 해당 후보 E2E·성능·복구 → 배포 → 실제 호스트 재검증.

현행 미커밋 구현을 보존한다. 문서 작업이 구현 파일을 임의로 커밋하거나 stage하지 않는다. 실제 구현 완료 후 변경 내용을 검토한 별도의 깨끗한 후보를 만든다.

현재 CSP의 EmailJS 예외와 README의 ‘전송 구조적 차단’ 문구는 일치시켜야 한다. 자동 telemetry·게임 자료·세이브 전송을 추가하지 않는다.

## 17. 납품 계약과 일정

### 17.1 매 묶음의 제출물

1. 해결한 플레이 경험과 전후 차이.

6. 진행 변경은 정상 플레이 시작/종료 세이브.

‘테스트 +45개’는 검증 수단의 변화다. 사용자 경험이 무엇만큼 완성됐는지는 별도 자료로 보여야 한다.

### 17.2 예상 일정

아래는 **전담 개발자 1명, 필요 시 3D 제작자·QA 지원이 있는 초기 범위 추정**이다. 약속된 납기나 실측값이 아니다.

| 묶음 | 예상 | 종료 조건 |
|---|---|---|
| PT-01/02 보강 | 3~7일 | 증거 공백·복합 복구 경계 해소 |
| PT-03 대표 구간 | 1~2주 | 첫 체육관까지 완성 기준 확정 |
| PT-04/05 월드·인물·행동 | 3~6주 | 고유 인물·13종 사물·주요 필드 행동 |
| PT-06/07 배틀·진행 | 3~5주 | 전체 진행 체인·전투·엔딩 |
| PT-08/09/10 품질 | 2~4주 | 실기·설치·저장·언어·입력 |

직렬 단순 합산으로 C1은 대략 **10~20주 + 선행 보강 3~7일**이다. 기존 코드 재사용 정도·대역 모델 제작량·원작 대조·기기 확보에 따라 달라진다. GPU 복구가 완료됐다는 이유만으로 3D 모델 제작과 전체 플레이 QA 비용을 0으로 잡지 않는다.

C2는 시설별 원작 조사 후 다시 산정한다. 네 프런티어 시설·콘테스트·지하통로를 모두 포함하면 추가 수개월 규모의 가능성이 있다. C1 일정에 몰래 포함하지 않는다.

일정이 부족하면 추가 장식·C2 범위를 줄인다. 저장 안전·메인 진행·주요 객체 가시성·정확한 검증을 희생하지 않는다.
