# 롬 데이터 지도 · 추출 설계

플래티넘 롬에서 무엇을 어떻게 꺼내는지에 대한 정본. [PLAN.md](PLAN.md)가 "무엇을 만들 것인가"라면 이 문서는 "원본이 어떻게 생겼는가"다.

**원칙: 포맷은 추측하지 않고 실측으로 확정한다.** 크기 합·값 분포·원작 대조 중 최소 하나로 검증되지 않은 구조는 "미확정"으로 표시한다. 이 프로젝트에서 이미 두 번, 그럴듯한 가설이 데이터에 반박당했다(charmap 오프바이원, BDSP 채널 매핑).

## 2. 확정된 포맷

### 2.1 map_matrix — 청크를 존으로 조립

```
u8   width, height
u8   hasHeaders, hasHeights
u8   nameLen;  char name[nameLen]
u16  headers[w*h]    // hasHeaders일 때. 값 = 존(맵 헤더) id
u8   heights[w*h]    // hasHeights일 때
u16  maps[w*h]       // land_data 파일 인덱스. 0xFFFF = 빈칸
```

289개 전부 크기 합이 정확히 일치한다. **#0이 신오 오버월드 30×30**(청크 468칸 사용). 나머지는 던전·건물 내부로 `m_dun0101_` 같은 이름이 붙어 있다.

### 2.2 land_data — 청크 하나

```
u32 permSize (항상 2048), objSize, modelSize, bdhcSize
u8  perm[permSize]      // 32×32 타일 × u16
u8  objects[objSize]    // 48B 단위 건물 배치
u8  model[modelSize]    // NSBMD ("BMD0")
u8  bdhc[bdhcSize]      // 높이 지오메트리 ("BDHC")
```

666개 전부 크기 합 일치, 전원 `BMD0` + `BDHC` 보유.

**타일 u16**: 최상위 비트(`0x8000`)가 통행 불가, 하위 비트가 거동. 오버월드 전체 어휘 **54종**.

| 값 | 의미 | 근거 |
|---|---|---|
| `0x0000` | 통행 가능 평지 | 최다 빈도, 통로 형태 |
| `0x8000` | 통행 불가 | 건물·절벽 윤곽과 일치 |
| `0x0015` | 풀숲(인카운터 추정) | 두 번째 최다, 넓은 덩어리 분포 |
| 나머지 51종 | **미확정** | 원시값으로 보존 |

> ⚠️ 처음에 타일당 u8로 읽어 체커보드 패턴이 나왔다. **u8/u16 착각의 전형적 증상**이니 다른 격자 데이터에서도 먼저 의심할 것.

**건물 배치 (48B)** — 20.12 고정소수점, `/65536`이 곧 타일 단위:

```
i32 modelId
i32 x, y, z        // 청크 중심 기준
i32 rotX, rotY, rotZ
i32 scaleX, scaleY, scaleZ   // 4096 = 1.0
i32 ?, ?           // 미확정
```

### 2.3 zone_event — NPC·워프·트리거

```
u32 countA; u8 A[countA * 20]
u32 countB; u8 B[countB * 32]
u32 countC; u8 C[countC * 12]
u32 countD; u8 D[countD * 16]
```

엔트리 크기 조합 `[20, 32, 12, 16]`은 **534개 전부를 정확히 소진하는 유일한 해**다(8~36B 후보 4096조합 탐색). 파일 인덱스 = 맵 헤더 id.

| 섹션 | 크기 | 총 엔트리 | 추정 |
|---|---|---|---|
| A | 20B | 682 | 간판·숨은아이템 |
| B | 32B | 3555 | **NPC** (최다·최대 엔트리) |
| C | 12B | 1213 | **워프** (문·계단) |
| D | 16B | 186 | 스크립트 트리거 타일 |

내부 필드는 **미확정**. 역할 추정은 엔트리 수·크기 근거일 뿐이므로, 실제 배치와 대조해 확정해야 한다.

### 2.4 pl_personal — 종족 데이터 (508개 × 44B)

모부기(#387) 전 필드를 원작과 대조해 확정했다.

| 오프셋 | 필드 | 모부기 |
|---|---|---|
| 0~5 | HP, 공격, 방어, **스피드**, 특공, 특방 | 55/68/64/31/45/55 |
| 6~7 | 타입1, 타입2 | 12, 12 (풀) |
| 8 | 포획률 | 45 |
| 9 | 기초 경험치 | 64 |
| 10~11 | EV 수득 (2비트×6) | 공격 1 |
| 12~15 | 야생 소지 아이템 ×2 | 없음 |
| 16 | 성비 | 31 (수컷 87.5%) |
| 17 | 부화 사이클 | 20 |
| 18 | 기초 친밀도 | 70 |
| 19 | 성장 곡선 | 3 (Medium Slow) |
| 20~21 | 알그룹 ×2 | 괴수, 식물 |
| 22~23 | 특성 ×2 | 65 (심록), 없음 |
| 24 | 대습지 도주율 | 0 |
| 25 | 색·반전 | 3 |
| 28~43 | 기술머신 학습 비트필드 (128비트) | — |

⚠️ **스탯 순서가 HP/공/방/스피드/특공/특방이다** — 표시 순서와 다른 4세대 내부 순서다. `@pkmn/sim`에 넘기기 전 재배열 필요.

## 3. 추출 파이프라인 설계

### 3.1 구조

```
tools/
  spike/          역공학용. 포맷을 뚫을 때만 쓰고 산출물은 신뢰하지 않는다
  extract/        정식 파이프라인. 여기 나온 산출물만 게임이 소비한다
    nds.js          롬 파일시스템
    narc.js         NARC 컨테이너
    text.js         메시지 뱅크 디코더 + 로케일 매핑
    maps.js         ✅ 존 → 타일·건물 JSON
    events.js       zone_event → NPC·워프·트리거 JSON
    species.js      personal/evo/wotbl → 종족 JSON
    moves.js        waza_tbl → 기술 JSON
    trainers.js     trdata/trpoke → 트레이너 JSON
    index.js        `pnpm extract --rom=...` 진입점
```

`tools/spike/`와 `tools/extract/`를 나누는 이유: 스파이크 코드는 **틀린 가설을 담고 있을 수 있다**. 실제로 charmap과 BDSP 채널 매핑이 그랬다. 정식 파이프라인은 검증된 것만 옮겨 담는다.

### 3.2 산출물 레이아웃

```
public/data/
  zones/T01.json          타일 격자 + 건물 배치 (✅ 구현됨)
  events/T01.json         NPC·워프·트리거
  species.json            508종 종족값·타입·특성·진화·레벨업기술
  moves.json              471기술
  trainers.json           928 트레이너
  dialogue/{en,ko,ja}/    뱅크별 텍스트
```

**전부 정적 JSON이다.** 런타임에 롬을 파싱하지 않는다 — 브라우저에서 128MB 롬을 다룰 이유가 없고, 로케일 3벌을 매번 디코드할 이유도 없다.

### 3.3 스키마

zod로 런타임 검증 + 타입 생성. 추출기가 스키마를 통과시킨 것만 쓴다 — 포맷 가정이 조용히 틀리는 것을 막는 마지막 방어선이다. `src/data/textBanks.test.ts`가 그랬듯, **검증된 값은 테스트로 고정**한다.

## 4. 다음 마일스톤 설계 — "걸어서 연결된 신오"

지금은 트윈리프타운 하나가 섬처럼 떠 있다. 이걸 **존 간 이동이 되는 세계**로 만드는 것이 다음 목표다. 새로운 미지가 필요 없고, 이미 뚫어둔 데이터만으로 도달할 수 있다.

### 4.1 구성 요소

**① 존 전환** — 두 종류를 구분해야 한다.

- **경계 전환**: 마을에서 도로로 걸어 나가기. 오버월드 행렬에서 인접 셀로 넘어가는 것이므로 워프가 아니라 **좌표 연속**이다. 존 경계에 도달하면 이웃 존을 로드하고 로컬 좌표를 이어 붙인다
- **워프 전환**: 문·계단. `zone_event`의 C 섹션(12B)이 목적지를 지정한다

경계 전환이 있어서 §4.2의 "청크 스트리밍"이 자연스럽게 필요해진다. 지금 `ZoneGrid`가 존 단위로 격자를 펴는데, **오버월드 전체를 하나의 격자로 펴는 편이 단순하다** — 30×30 청크 × 32타일 = 960×960 타일 = 921,600칸 × 2B = **1.8MB**. 메모리에 통째로 올려도 된다. 청크 스트리밍은 렌더링에만 적용하면 된다.

> 이건 기획서 §4.2의 설계를 단순화하는 발견이다. 충돌 격자는 스트리밍할 필요가 없다.

**② NPC 배치** — `zone_event` B 섹션. 32B 안에 위치·모델·이동유형·스크립트가 들어 있을 것으로 추정되나 **필드 배치 미확정**이라 먼저 해독이 필요하다. 해독 방법: 트윈리프(NPC 3명)처럼 개수가 적고 원작 배치를 아는 존에서 좌표로 보이는 값을 찾아 실제 위치와 대조한다.

**③ 인카운터** — 풀숲 타일(`0x0015` 추정)을 밟으면 확률 판정. `pl_enc_data` 424B 고정 구조 해독 필요. 424 = 대략 (2 + 12×2)×... 슬롯 12개 구조가 4세대 표준이므로 그 가정으로 검산한다.

### 4.2 진행 순서

새 미지의 크기 순으로 배열했다 — 작은 것부터 처리해 큰 것에 쓸 시간을 벌어둔다.

| 순서 | 작업 | 새 미지 | 결과 |
|---|---|---|---|
| 1 | `species.js` + `moves.js` + zod 스키마 | 거의 없음 (레코드 고정 크기) | 배틀 데이터 완비 |
| 2 | 오버월드 전역 격자 + 경계 전환 | 없음 | **신오를 끝에서 끝까지 걸을 수 있다** |
| 3 | `events.js` — 워프 섹션 해독 | 12B 필드 배치 | 건물 출입 |
| 4 | 인카운터 테이블 해독 | 424B 필드 배치 | 야생 조우 |
| 5 | NPC 섹션 해독 + 배치 | 32B 필드 배치 | 마을이 살아난다 |
| 6 | `scr_seq` 오퍼레이션 | **큼** | 이벤트·대화 |

2번이 체감 도약이 가장 크다. 트윈리프에서 202번 도로까지 걸어가는 순간 "신오지방"이 실체가 된다.

### 4.3 미루는 것과 이유

- **BDHC(높이)** — 평지 존에서는 필요 없다. 트윈리프·201·202는 전부 평지다. 언덕·계단이 있는 존에 도달할 때 다룬다
- **NSBMD 지오메트리** — §4.2대로 아트는 자체 제작이다. 블록아웃 레퍼런스가 필요해지는 시점(맵 아트 착수)까지 미룬다
- **`scr_seq`** — 가장 크고 가장 나중이다. 대화·이벤트가 없어도 걸어다니고 조우하고 싸울 수 있다
