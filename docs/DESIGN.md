# 화면은 어떻게 생겼는가 — 창 한 벌

**이 문서는 「무엇을 그리는가」가 아니라 「무엇으로 그리는가」다.** 어느 화면에
무엇이 뜨는지는 [PARITY.md](PARITY.md), 자리와 배치는 [CODEMAP.md](CODEMAP.md)
§2.5가 정본이고, 여기는 **색·테두리·모서리·글꼴을 어디서 가져오는가**만 정한다.

규칙은 하나다.

> **`src/ui/theme/`에서만 가져온다. 화면 파일에 색을 적지 않는다.**

---

## 0. 왜 이 문서가 생겼나

한때 화면마다 창을 새로 그렸다. 테마 계약에 토큰이 7개인데 화면에는 hex 140개와
`rgba()` 189벌이 박혀 있었고, 그림자 처방이 48벌, 모서리 값이 18가지였다. 창
재질만 여덟 벌이었다 — 필드는 밝은 창, 메뉴는 남색 창, 배틀은 반투명 유리,
설치 화면은 또 다른 카드였다. **X를 누르는 순간 다른 게임으로 넘어갔다.**

각각은 멀쩡했다. 모아 놓으면 한 게임이 아니었다. 그리고 그 상태의 화면은
「게임」이 아니라 **다크 모드 관리자 앱**으로 읽힌다 — 자간 벌린 작은 라벨,
반투명 흰 판, 1px 실선, 크게 번지는 그림자, 제목 옆 색 세로줄, 알약 단추.
이 목록은 지어낸 것이 아니라 「AI가 만든 화면」을 알아보는 표식으로 널리
꼽히는 것들이고, 그때 우리 화면이 그 목록을 그대로 만족했다.

⚠️ **주석으로 「같은 것을 쓴다」고 적는 것은 안 통한다.** `startMenu.css.ts`가
「전체 화면 메뉴와 같은 테두리·같은 띠를 쓴다」고 적어 놓고 바로 아래에서 값을
손으로 베꼈고, 그 사이 `EDGE` 한 줄은 알파가 넷으로 갈라져 있었다. **값은 한
곳에서 import로 와야 한다.**

---

## 1. 실측 — 창은 BDSP의 것이다

값을 눈으로 고르지 않는다. 아래는 전부 원본 자산에서 잰 것이다.

### 1.1 창 (`UIs/shareduiassets/sharedui` 아틀라스)

BDSP의 공용 창 하나를 아틀라스에서 꺼내 단면을 쟀다.

| | 잰 값 |
|---|---|
| 테두리 | `#7bb1e7` — 위쪽이 `#8ac1f2`로 밝고 안쪽이 `#6fa0d2`로 어둡다 |
| 안쪽 (위 → 아래) | `#f7fdfe` → `#e5ffff` (30%) → `#d4ebf1` (50%) → `#cae2e8` (70%) → `#c3dae2` |
| 그림자 | **없다.** 테두리 바깥은 알파 0이다 |
| 결 | 안쪽에 1px 가로줄이 일정 간격으로 깔려 있다 (줄 친 종이 같은 결) |
| 모서리 | 폭의 4~5%. 469px 창에 20px쯤 |

⚠️ **창은 밝다.** 우리 메뉴가 남색이었던 것은 원본과 무관한 선택이었다. 창이
밝으면 글자는 어둡고, 그러면 뒤의 3D를 흐리게 깔 이유도 사라진다.

⚠️ **그림자를 붙이지 않는다.** `0 22px 56px rgba(0,0,0,0.62)` 같은 것은 원본에
없다. 판을 띄우는 것은 그림자가 아니라 **테두리**다.

### 1.2 고른 것 (같은 아틀라스)

| | 잰 값 |
|---|---|
| 고른 창의 테두리 | `#d7b319` (금) — 안 고른 것은 `#7bb1e7` (파랑) |

⚠️ **고른 것을 경고색으로 가리키지 않는다.** 한때 `hud.warn`(`#ff6b5e`)이
고른 줄의 선이자 화면 제목의 장식이자 도감의 점이었다. 한 색이 셋을 나르면
그 색은 아무 뜻도 안 나른다.

⚠️ **어디서나 같은 표시다** — 목록 줄, 파티 카드, 가방 주머니 탭, 배틀 명령 칸,
타이틀 단추가 전부 금 테두리다. 배틀 명령은 한때 **그 칸의 색으로 판을 통째로
채웠는데**, 창이 밝아진 뒤로는 빨간 판 위의 빨간 글씨가 됐다. 왼쪽 색 조각이
이미 어느 칸인지를 나르므로 판까지 칠할 이유가 없다.

### 1.3 막대 (같은 아틀라스)

BDSP의 막대는 **짙은 테두리 안에 광택이 있는 채움**이다.

| | 잰 값 |
|---|---|
| 테두리 | `#474747`, 굵다 (막대 높이의 1/6쯤) |
| 빈 칸 | `#ffffff` → `#f5f5f5` |
| 채움 | 위에 밝은 줄 한 겹, 본색, 아래에 어두운 줄 한 겹 |

### 1.4 HP 색 (`raw/decomp/res/graphics/party_menu/menu.pal`)

BDSP 아틀라스에 있는 초록·분홍 막대는 **타입 막대**지 HP 막대가 아니다. HP는
원작 팔레트에서 온다 — `PartyMenu_DrawMemberHealthbar`가 팔레트 세 벌을 갈아
끼우고 색 9·10만 쓴다 (`party_menu/windows.c:964`).

| 상태 | 밝은 쪽 (색 9) | 본색 (색 10) | 언제 |
|---|---|---|---|
| 초록 | `#62ff62` | `#18c520` | 남은 HP > 1/2 |
| 노랑 | `#ffde00` | `#eeac00` | > 1/5 |
| 빨강 | `#ff9c9c` | `#ff4a39` | > 0 |
| 빈 칸 | `#a4ac94` | `#6a7362` | 0 |

경계는 `App_BarColor` (`raw/decomp/src/unk_0208C098.c:51`)가 정본이다 —
**1/2과 1/5**이지 70%·30% 따위가 아니다.

막대 자체는 4픽셀이다: 본색 1줄 · 밝은 쪽 2줄 · 본색 1줄
(`Window_FillRectWithColor` 세 번). 그래서 우리 막대도 위아래에 어두운 선이
있고 가운데가 밝다.

⚠️ **여기 있는 값을 남의 디자인 시스템에서 가져오지 않는다.** 한때 HP 빨강이
Material Red 400(`#ef5350`), 기절이 Tailwind gray-500(`#6b7280`), HUD 강조가
Android 브랜드 초록(`#3ddc84`)이었다. 예뻐 보여서 고른 값이고, 그래서 다른
게임의 막대처럼 보였다.

### 1.5 상태 이상 딱지 (`pokemon_summary_screen/status_icons.{png,pal}`)

딱지 일곱이 24×8로 세로로 쌓여 있고 차례가 `SUMMARY_CONDITION_*`이다. 띠 하나가
**첫 줄·몸통·끝 줄** 색 셋이다 (글자는 전부 흰색).

| 상태 | 첫 줄 | 몸통 | 끝 줄 |
|---|---|---|---|
| 포켓러스 | `#9ca48b` | `#6a7362` | `#525a4a` |
| 마비 | `#ffd529` | `#eeac00` | `#bd7b00` |
| 얼음 | `#31cdcd` | `#009c9c` | `#006a6a` |
| 잠듦 | `#9ca48b` | `#6a7362` | `#525a4a` |
| 독 | `#e65a4a` | `#c541cd` | `#b40000` |
| 화상 | `#ff9c8b` | `#e65a4a` | `#b40000` |
| 기절 | `#e65a4a` | `#b40000` | `#730000` |

⚠️ **잠듦과 포켓러스가 같은 색이다.** 눈으로 고른 것이 아니라 그림에서 그대로
나온 값이라 안 벌린다. 독도 몸통만 자홍이고 테두리는 화상 쪽 붉은색이다.

⚠️ **맹독 딱지는 없다.** `PokemonSummaryScreen_StatusIconAnimIdx`가
`MON_CONDITION_POISON | MON_CONDITION_TOXIC`을 한 딱지로 묶는다 — 색을 따로
만들면 원작에 없는 구분이 생긴다.

⚠️ 한때 이 값들이 우리가 고른 색이었다 (`#a25bc4` 독, `#7b8794` 잠듦…).
그리고 요약 화면의 포켓루스 딱지가 **분홍**이었는데, 실측해 보니 잠듦과 같은
회록색이고 성별 색과는 아무 상관이 없었다.

### 1.6 파티 판 (`party_menu/menu.pal`)

`application->colors`가 팔레트 **3행부터**고, 판 색은 고른 것이 `+4`·기절이
`+2`다 (`party_menu/main.c:1420`). 곧 보통이 3행, 기절이 5행이다. 옮겨 오는
것은 램프의 밝은 끝(색 4)과 짙은 끝(색 7)이다.

| 상태 | 밝은 끝 | 짙은 끝 |
|---|---|---|
| 보통 | `#9cc5f6` | `#416a9c` |
| 기절 | `#dea452` | `#943900` |

⚠️ **판 색은 자리가 아니라 상태다.** `Bg_ChangeTilemapRectPalette(…, 3 + slot)`만
보면 여섯 자리가 여섯 색인 것처럼 읽히는데, 그 행에 무엇을 싣는지가
`main.c:1420`에서 상태로 정해진다 — 여섯 판이 여섯 색인 것이 아니다.

⚠️ **고른 판은 우리 금 테두리를 쓴다.** 원작은 고른 판의 팔레트를 하늘색으로
갈아 끼우는데, 그러면 「고른 것」 표시가 이 화면에서만 달라진다 (§1.2).

### 1.7 어떻게 다시 재나

```
py -3.13 tools/spike/uiTexDump.py "UIs/shareduiassets/sharedui"   # BDSP 아틀라스를 PNG로
py -3.13 tools/spike/dpptGfxDump.py bag                           # DPPt 가방 화면·가방 그림
py -3.13 tools/spike/dpptGfxDump.py party                         # DPPt 파티 화면
```

DPPt 쪽은 화면 한 장이 **타일셋 + 타일맵 + 팔레트** 셋으로 흩어져 있어서 셋을
합쳐야 원작이 실제로 무엇을 그렸는지 보인다. 팔레트만 필요하면
`res/graphics/**/*.pal`이 JASC-PAL 텍스트라 그냥 읽으면 된다.
떨군 것은 `.audit/`에 남는다 (Git 무시 — 원본 픽셀이라 커밋하지 않는다,
COPYRIGHT.md §5). 여기서 가져오는 것은 색 몇 개와 자리 몇 개뿐이고, 그 값만
`theme/day.css.ts`에 적힌다.

## 2. 어디서 가져오나

```
src/ui/theme/
  contract.css.ts   토큰 이름 (createThemeContract) — CSS 변수가 된다
  day.css.ts        토큰 값 — §1의 실측이 여기 한 번만 적힌다
  fonts.css.ts      @font-face와 폴백 목록 (§4)
  window.css.ts     창 한 벌·막대·목록 줄·커서·덮개. 화면이 실제로 쓰는 것
  scale.ts          숫자 상수 (모서리·테두리·여백·글자·시간). CSS 변수가 아닌 것
```

화면 파일이 하는 일:

```ts
import { vars } from '../theme/contract.css'
import { GAP, RADIUS, TEXT } from '../theme/scale'
import { RULE, WINDOW, row, rowOn } from '../theme/window.css'

export const box = style({ ...WINDOW, padding: GAP.wide })
export const head = style({ borderBottom: RULE, color: vars.ink.strong })
```

**금지:**

- `#`으로 시작하는 값을 화면 파일에 적지 않는다. 색은 `vars.*`나 `window.css`에서 온다.
- `boxShadow`를 새로 쓰지 않는다. 창은 그림자로 뜨지 않는다.
- `borderRadius`에 숫자를 직접 적지 않는다. `RADIUS.*`를 쓴다.
- `backdrop-filter`를 쓰지 않는다. 반투명 유리는 원본에 없다.
- `letterSpacing`을 쓰지 않는다. 한국어에 자간을 벌릴 이유가 없고, 벌린 작은
  라벨은 그 자체가 웹앱의 말투다.
- `borderLeft`로 제목을 장식하지 않는다.
- `borderRadius: 999` 알약을 쓰지 않는다. 원작에 알약 UI가 없다.

⚠️ **이 금지 목록은 `pnpm lint`가 실제로 잡는다** (`eslint.config.js`의
`no-restricted-syntax`). 문서에만 적힌 규칙은 지켜지지 않는다는 것을 이미 한 번
확인했다.

## 3. 창이 몇 벌인가 — 한 벌이다

| 무엇 | 어디 |
|---|---|
| 필드 대사창 · 예/아니오 · 간판 | `WINDOW` |
| 메뉴 화면 전부 (시작 메뉴 포함) | `WINDOW` |
| 배틀 체력판 · 명령 칸 | `WINDOW` (불투명하다. 유리가 아니다) |
| 설치 화면 | `WINDOW` |
| 포켓치 | **예외.** 손에 든 기계다 — `vars.device` (회색 몸체·초록 LCD) |
| 트레이너 카드 | **예외.** 카드 한 장이다 — `vars.card`. 단 광택·대각 그러데이션은 안 쓴다 |
| 간판 판 | **예외.** 나무 판이다 — `vars.sign` (`DrawSignpostFrame`) |
| 모험노트 · 상장 | **예외.** 종이다 — `vars.paper` |
| 개발용 계기판 (`?dev=1`) | **예외.** 게임 위에 얹는 연장이라 일부러 게임 창이 아니다 — `vars.dev`. 배포물에는 안 실린다 |

예외는 전부 **물건을 그린 것**이거나 게임이 아닌 것이고, 그래도 **값은
`ui/theme/`에서 온다.** 그 밖에 예외를 늘리지 않는다 — 여덟 벌이 됐던 것이
그렇게 시작했다.

## 4. 글꼴

| 어디 | 무엇 | 왜 |
|---|---|---|
| 대사창 | **Galmuri11** | 한글 픽셀 글꼴. 원작 대사창이 픽셀 글꼴이다 |
| 그 밖의 UI | **Pretendard** (서브셋) | 본문·목록·숫자 |
| 일본어 UI | **Noto Sans JP** (가나만, 33KB) | Pretendard 서브셋에 가나가 **한 자도 없다** |
| 숫자 칸 | Pretendard + `font-variant-numeric: tabular-nums` | 자릿수가 흔들리면 목록이 흔들린다 |

일본어를 어떻게 정했는지는 재 본 것이 정본이다 (`fontTools`로 cmap을 세고,
`public/data`의 글 파일 496개에서 글자를 뽑아 대조했다).

| 잰 것 | 값 |
|---|---|
| 일본어 게임 텍스트의 글자 종류 | 306종 — 가나·전각기호뿐, **한자 0자** |
| Galmuri11이 들고 있는 것 | 한글 11,172 · 가나 187 · 한자 6,477 |
| Galmuri11에 없는 것 (일본어) | `⋯` `㊚` `㊛` 셋 |
| Pretendard 서브셋에 없는 것 (일본어) | 223자 — 가나 전부 |

그래서 **일본어 픽셀 글꼴(PixelMplus)은 안 싣는다.** 대사창은 Galmuri11로
이미 나오고, 진짜 구멍은 UI 쪽이었다. 가나·전각기호 블록만 잘라 낸 33KB짜리
서브셋을 `tools/fonts/jpSubset.py`가 굽는다 (`pnpm gen:jpFont`).

⚠️ **서브셋에 한자를 안 넣는다.** 넣으면 `unicode-range`에 한자가 들어가고,
그러면 한국어 화면의 한자까지 일본 자형으로 끌려간다 — 아래 폴백 순서 문제와
같은 것이다. 일본어 게임 텍스트에 한자가 없으니 넣을 이유도 없다.

⚠️ **`unicode-range`에는 Pretendard에 없는 글자만 적는다.** 겹치면 두 가지가
한꺼번에 나빠진다: 늦게 선언된 쪽이 이기므로 한국어 화면이 그 글자를 일본
자형으로 그리고, `unicode-range`가 곧 다운로드 조건이라 **그 글자 하나 때문에
일본어 글꼴을 통째로 받는다.** 실제로 그랬던 것이 `U+2026`과 `U+3008-300F`
(… 〈〉《》「」『』) 아홉 자다 — 타이틀·설치 화면의 한국어 안내문이 낫표를 쓰는데
(「시작」·「세이브 파일 불러오기」), 전각 낫표가 문장에 빈칸을 내면서 첫 방문마다
33.8kB가 나갔다. 두 글꼴의 cmap을 fontTools로 세어 겹치는 것이 정확히 그 아홉
자임을 확인하고 범위에서 뺐다 (DEPLOY.md §3).

⚠️ 한국어 글 세 뱅크(16·441·697)에 **조합용 자모**(U+1100 계열)가 들어 있는데
어느 글꼴에도 없어서 두부로 뜬다. 이름 짓기 자판의 줄(`ㄱㄴ` `ㄷㄹ` …)이고,
우리 이름 화면은 원작 자판을 안 그려서 아직 화면에 안 나온다. 고칠 자리는
글꼴이 아니라 charmap이다.

⚠️ **시스템 글꼴로 두지 않는다.** `'Segoe UI'`로 돌던 동안에는 무엇을 더 손봐도
화면이 게임으로 안 읽혔다. 화면에서 제일 크게 티가 나는 한 줄이다.

⚠️ **글꼴 파일은 `public/fonts/`에 두고 `@font-face`로 싣는다.** 구글 폰트 CDN을
부르지 않는다 — 오프라인에서 도는 게임이고(PLAN §4.6), 첫 화면이 남의 서버를
기다리면 안 된다. 서비스 워커는 **처음 쓸 때** 셸 캐시에 넣는다(빌드된 js·css와
같은 길). 미리 받는 목록에는 안 넣는다 — 글꼴이 안 와도 폴백으로 화면은 선다.

⚠️ **한자 글꼴은 순서가 곧 나라다.** 폴백 목록에서 일본어 글꼴을 한국어 글꼴보다
앞에 두면 **한자만** 일본 자형으로 간다. 같은 코드포인트라 눈으로만 갈린다.

## 5. 배치 — 화면이 비면 안 된다

창 한 벌을 정해도 배치가 웹앱이면 웹앱으로 보인다.

- **왼쪽 목록 / 오른쪽 상세로 가르지 않는다.** 그건 설정 앱의 배치다. 둘 다
  원작 배치를 실측해서 옮겼다.
  - **가방** (`applications/bag/windows.c`): 왼쪽 0~112px에 가방이 서고 그 아래
    주머니 아이콘 여덟과 이름표, 오른쪽 14타일(112px)부터가 도구 목록,
    18타일(144px)부터 **화면 폭 전체**가 설명이다. 가방 그림은 주머니마다
    다른 칸이 열린 여덟 장이고 `ManagedSprite_SetAnim(BAG_SPRITE_BAG,
    pocketType)`이 고른다. 굽는 것은 `tools/extract/bagSprite.js`와
    `src/import/platinum/bagSprite.ts` **둘 다**다.
    ⚠️ **주머니마다 바탕색이 바뀌지 않는다.** 한때 여기에 그렇게 적혀 있었는데
    `bag_ui_main.NSCR`이 팔레트 행 셋을 고정으로 쓰고, 주머니가 바뀔 때
    바뀌는 것은 가방 그림뿐이다. 색이 바뀌는 것은 다른 세대다.
  - **파티** (`sMemberPanelTemplates`): 판 하나가 16×6타일(128×48)이고 두 줄
    세 칸인데 **오른쪽 줄이 한 타일 내려가 있다** (왼쪽 y=0·6·12, 오른쪽
    y=1·7·13). 판이 화면 아래까지 내려와서 빈자리가 안 남는다. 능력·기술을
    세우는 오른쪽 칸은 원작에 없다 — 능력은 요약 화면이 맡고, 갈래 메뉴는
    판 위에 창 하나로 뜬다.
- **창은 화면이 아니다.** 원작은 256×192 안에 전부 담는다. 화면이 넓어지면 창이
  커지는 게 아니라 **여백이 커진다**.
- **안 고른 줄은 아무것도 아니다.** 줄마다 판을 깔면 목록이 아니라 카드 더미다.
- **빈자리를 남기지 않는다.** 물건 하나를 넣었을 때 화면의 85%가 빈 것은 창
  크기를 내용이 아니라 화면에 맞췄다는 뜻이다.

## 6. 무엇을 지어내도 되나

원작에 없는 화면이 있다 — 설치 화면, 조작 안내, 개발용 계기판. 그것도 **창은
같은 것을 쓴다.** 지어내도 되는 것은 *무엇을 담는가*지 *무엇으로 그리는가*가
아니다.

⚠️ 특히 설치 화면은 사람이 이 게임에서 **제일 먼저 보는 화면**이다. 여기가
온보딩 페이지처럼 생기면 그다음에 무엇이 나오든 그 인상으로 읽힌다.
